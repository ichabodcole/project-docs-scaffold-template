# Agent-Native Work Systems: Units, Fields, and File Layouts (2025–2026)

Scope: agent-native and file-based work systems from 2025–2026 — tools built
specifically around handing bounded work to a coding agent and getting state
back, as opposed to general PM tools with agents bolted on. This report goes
beyond the
[2026-09-03 file-based work-tracking landscape report](../../work-cycle-taxonomy-landscape/reports/2026-09-03-file-based-work-tracking-landscape-report.md)
(RFC/KEP/PEP/RFD, ADRs, git-bug/ticgit/Radicle, PARA, first look at beads) and
does not redo it.

**Reading key for the comparison table and each section:** every primitive is
tagged **[ENTITY]** (a thing with its own identity and file/record), **[STATE]**
(a field recording where an entity has got to), or **[VIEW]** (a grouping or
lens over entities — folder-by-status, board column, generated list). This
sorting is the frame the parent investigation asked for: what are the
fundamental things, and how do they compose.

## GitHub Spec Kit

**What it is.** An open-source toolkit from GitHub (github/spec-kit, MIT
license) that layers a spec-first workflow on top of an existing coding agent
(Claude Code, Copilot, Codex, Cursor, Gemini, and 38 integrations total) via
slash commands. Confirmed to exist and actively maintained as of 2026.
[github/spec-kit](https://github.com/github/spec-kit),
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

**Unit handed to the agent.** A **task** inside `tasks.md` — one checklist line
per deliverable, tagged `[P]` when it can run in parallel with siblings. Above
it sit two other artifacts the agent also consumes: `spec.md` [ENTITY]
(requirements, user stories, acceptance criteria, `[NEEDS CLARIFICATION]`
markers) and `plan.md` [ENTITY] (architecture, "Phase -1 Pre-Implementation
Gates," complexity tracking). Tasks themselves are **[ENTITY]** in aggregate
(the file) but each checklist line is closer to a **[VIEW]** row than an
independently addressable record — there is no per-task ID scheme beyond its
line and no per-task frontmatter.
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

**Size.** A task is a single deliverable extracted from a plan's contracts and
data model — smaller than Kiro's or Task Master's tasks, closer to a checklist
item than a story.

**Fields.** Spec: user stories + acceptance criteria + non-functional
requirements + a completeness checklist. Plan: technology rationale, gate
checks, requirement traceability. Tasks: deliverable description, `[P]` parallel
marker, prerequisites/dependencies expressed as ordering in the list rather than
a typed field. No status field is documented on individual tasks; progress is
tracked by which checklist boxes are checked.
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

**Spec → plan → tasks relationship.** Strictly linear and each stage writes a
new file: `/speckit.specify` → `spec.md`; `/speckit.plan` → adds `plan.md`,
`research.md`, `data-model.md`, `contracts/`, `quickstart.md`; `/speckit.tasks`
→ adds `tasks.md`, generated by analyzing the plan and design docs.
[github/spec-kit AGENTS.md](https://github.com/github/spec-kit/blob/main/AGENTS.md).

**File layout.**

```
specs/[branch-name]/
├── spec.md
├── plan.md
├── research.md
├── data-model.md
├── contracts/
├── quickstart.md
└── tasks.md
```

One directory per feature branch — the branch name is the grouping key, an
implicit **[VIEW]** rather than an authored one.
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

**State write-back.** Checklist boxes in `tasks.md` are checked as work
completes; the spec/plan/task files themselves are versioned via normal git
branches and merges — "Specifications are versioned, created in branches, and
merged." No separate state file or database.
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

**Human review.** At each stage boundary: PMs review acceptance criteria,
architects review the plan's technical decisions, and the branch is reviewed
before merge — the normal PR gate, not a bespoke UI.
[spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md).

## AWS Kiro Specs

**What it is.** A feature of Kiro, AWS's agentic IDE, confirmed live in Kiro's
own docs as of 2026. [kiro.dev/docs/specs](https://kiro.dev/docs/specs/).

**Unit handed to the agent.** A **task** in `tasks.md`, generated from
`requirements.md` and `design.md`. Two workflow variants exist:
Requirements-First (requirements → design → tasks) and Design-First (design →
requirements).
[kiro.dev/docs/specs/feature-specs](https://kiro.dev/docs/specs/feature-specs/),
[tech-design-first](https://kiro.dev/docs/specs/feature-specs/tech-design-first/).

**Fields.** `requirements.md` uses **EARS notation** ("WHEN [condition] THE
SYSTEM SHALL [behavior]") for user stories and acceptance criteria — a
distinctive, testable requirement grammar not seen elsewhere in this survey.
`design.md` holds architecture and sequence diagrams. The exact per-task
frontmatter in `tasks.md` (IDs, status, dependency fields) is **not documented
on the public pages fetched** — Kiro's docs describe task _execution_ ("Kiro
analyzes dependencies between tasks and runs independent tasks concurrently")
implying a dependency field exists, but the schema itself is unconfirmed from
primary sources; treat as **Medium confidence / unconfirmed**.
[kiro.dev/docs/specs](https://kiro.dev/docs/specs/).

**Spec → design → tasks relationship.** All three files are kept in the
conversation context together — "Kiro automatically includes all spec files ...
to ensure responses align with your documented specifications" — so tasks aren't
handed off in isolation; the agent always has the full spec chain.
[kiro.dev/docs/specs](https://kiro.dev/docs/specs/).

**File layout.** One directory per spec with `requirements.md`, `design.md`,
`tasks.md` as siblings (exact top-level path, e.g. `.kiro/specs/<name>/`, is
reported by third-party guides but not verified against Kiro's own docs in this
pass — **unconfirmed**).

**State write-back and human review.** Task completion is tracked via a "Run all
Tasks" button in the IDE; monitoring is described as "Monitoring progress across
discrete implementation tasks," but the mechanics of how a task's status is
persisted to the file (checkbox vs. frontmatter field) were **not found** on the
pages fetched — flagged as an open gap below.
[kiro.dev/docs/specs](https://kiro.dev/docs/specs/).

## Backlog.md

**What it is.** An open-source, local-first CLI + web UI (MrLesk/Backlog.md,
MIT, npm/bun/brew/nix) that turns a folder into a markdown-native Kanban board
explicitly designed for human/agent collaboration in a git repo. Confirmed
active as of 2026, with MCP support for Claude Code, Codex, Gemini CLI.
[MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md).

**Unit handed to the agent.** A **task**, one plain `.md` file per task, with
YAML frontmatter.

**Fields (frontmatter).** `id` (prefixed, e.g. `TASK-1`, configurable),
`status`, acceptance criteria (a checklist inside the body, "verifiable scope
per task"), `dependencies` (which tasks this one waits on / unblocks), optional
`parent` for hierarchy, and `milestone` for grouping bigger efforts.
[MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md),
[TerminalDock overview](https://terminaldock.com/backlog-md).

**File layout — state as folder, confirmed.** This is the clearest example in
the survey of **state encoded as file location, not only as a field**:

```
backlog/
├── config.yml
├── tasks/     # task-{id} - {title}.md  — active tasks
├── drafts/    # draft-{id} - {title}.md — not yet promoted
├── docs/      # doc-{id} - {title}.md
├── decisions/ # decision-{id} - {title}.md
└── archive/   # completed/archived tasks and drafts
```

"The status field determines which folder a task belongs to — active tasks go in
`backlog/tasks`, drafts go in `backlog/drafts`, and archived/completed items are
moved to `backlog/archive`." So Backlog.md keeps a `status` **[STATE]** field in
frontmatter _and_ mirrors it into a directory **[VIEW]** by moving the file on
transition — the folder is a materialized view of the field, kept in sync by the
CLI, not an independent source of truth.
[GitHub issue #1029 discussion + repo structure](https://github.com/MrLesk/Backlog.md/issues/1029),
[DeepWiki structure notes](https://deepwiki.com/saxster/Backlog.md).

**State write-back.** `backlog task edit <id> --status "In Progress"` (CLI),
drag-and-drop in the web Kanban board, or direct MCP tool calls from an agent —
all three write the same frontmatter field and, where relevant, move the file.
`--json` output keeps stdout machine-readable for scripting.
[MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md).

**Human review.** Three checkpoints are named explicitly: spec review (before
implementation), plan review (before coding), and code review (PR). Notably,
Backlog.md's own pitch is that a human can "read a screenful of task specs with
acceptance criteria before any code exists, and push back while a
misunderstanding is still one sentence" — review is designed to happen _before_
agent execution, not only after.
[MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md).

## Beads (Steve Yegge)

**What it is.** An open-source, distributed issue tracker built specifically as
external memory for coding agents (gastownhall/beads, Go, MIT), released October
2025 by Steve Yegge, addressing the "agents lose all memory between sessions"
problem he calls "50 First Dates."
[gastownhall/beads](https://github.com/gastownhall/beads),
[Steve Yegge, Medium](https://steve-yegge.medium.com/the-beads-revolution-how-i-built-the-todo-system-that-ai-agents-actually-want-to-use-228a5f9be2a9).

**Unit handed to the agent.** An **issue** ("a bead"), addressed by a hash-based
ID (`bd-a1b2`) to avoid merge collisions across agents working in parallel.
Hierarchical IDs express nesting: `bd-a3f8` (epic) → `bd-a3f8.1` (task) →
`bd-a3f8.1.1` (subtask) — the ID itself encodes the parent/child **[ENTITY]**
relationship rather than a separate `parent` field.
[gastownhall/beads](https://github.com/gastownhall/beads).

**Fields.** `status` (**[STATE]**: ready, claimed, in_progress, closed),
`priority` (P0/P1…), `type` (bug, task, message, epic), `dependencies` (blocker
edges — closing a blocker makes dependents "ready"), `assignee` (set atomically
on claim via `bd update <id> --claim`).
[gastownhall/beads](https://github.com/gastownhall/beads).

**File layout / storage — the outlier of this survey.** Not flat markdown. Beads
stores issues in **Dolt**, a version-controlled SQL database with git-like
branch/merge semantics, either embedded (`.beads/embeddeddolt/`, single writer)
or as a server for concurrent writers. A `.beads/issues.jsonl` export exists for
human/diff viewing and interchange but is explicitly **not** the source of
truth. Cross-machine sync goes through `bd dolt push/pull` against the same git
remote the code lives in.
[gastownhall/beads](https://github.com/gastownhall/beads). This is a real
departure from every other system in this report: Beads treats "flat markdown
files" as a lossy export of a database, not the record itself — relevant to
project-docs' choice to keep markdown-in-git as the source of truth.

**State write-back.** Agents query `bd ready` for unblocked, actionable work and
claim atomically; state changes (status + assignee together) are written as a
single transaction, not a field edit a human/agent could race against.
[gastownhall/beads](https://github.com/gastownhall/beads).

**Human review.** `bd show <id>` displays task detail plus an audit trail;
`bd ready --json` surfaces prioritized queryable work for a human to scan.
Persistent cross-session notes (`bd remember`) surface again during an agent's
planning phase via `bd prime` — a memory mechanism layered on top of the issue
graph, closer to Guidance Lifecycle's territory than pure work-tracking.
[gastownhall/beads](https://github.com/gastownhall/beads).

## Taskmaster AI (task-master-ai / Claude Task Master)

**What it is.** An open-source, PRD-to-tasks system
(eyaltoledano/claude-task-master, npm package `task-master-ai`) that plugs into
Cursor, Claude Code, Windsurf, Roo and others via MCP. Confirmed active as
of 2026.
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

**Unit handed to the agent.** A **task**, optionally broken into **subtasks**.

**Fields.** `id`, `status` (e.g. in-progress, done), `dependencies` (links to
prerequisite task IDs), `priority`, and a `testStrategy` field that functions as
acceptance criteria/verification instructions rather than a separate checklist.
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

**PRD → tasks relationship.** A human or agent runs "parse my PRD at
`scripts/prd.txt`," and Task Master decomposes the PRD into the structured task
set — the PRD is consumed once at generation time rather than kept live in
context the way Kiro keeps spec files present throughout.
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

**File layout.** `tasks.json` as the central manifest plus individual task files
under `.taskmaster/tasks/` — a dual representation (one aggregate file for
querying, one file per task for per-task diffs/context), unlike Backlog.md
(files only) or Spec Kit (one shared `tasks.md`).
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

**State write-back.** The agent writes status updates, subtask completions, and
dependency resolutions back to both `tasks.json` and the individual task file
automatically as it works — described as automatic rather than a separate CLI
invocation step, distinct from Backlog.md's explicit `edit --status` call.
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

**Human review.** Conversational: "Show me tasks 1, 3, and 5," "Can you help me
implement task 3?" — the agent presents task summaries and acceptance criteria
for approval before executing, inside the same chat session rather than a
dedicated board UI (Task Master does not ship a first-class web UI comparable to
Backlog.md's).
[eyaltoledano/claude-task-master](https://github.com/eyaltoledano/claude-task-master).

## AGENTS.md

**What it is.** Not a task-unit format — a **project-level context file**, now a
Linux Foundation-stewarded open standard, read natively by Claude Code, Codex
CLI, Cursor, Aider, Devin, GitHub Copilot, Gemini CLI, Windsurf, and Amazon Q as
of early 2026, with 60,000+ repos using it. Plain markdown, no required fields,
no YAML frontmatter, no special syntax — the agent just reads the prose.
[agents.md](https://agents.md/),
[AGENTS.md spec discussion, ASDLC.io](https://asdlc.io/practices/agents-md-spec/).

**Relevance to the taxonomy.** AGENTS.md is a **[VIEW]** onto the codebase
itself (build/test commands, code style, structure, git workflow, operational
boundaries) — it carries no work-item identity, no status, and closes no work.
In a monorepo, the closest AGENTS.md to the file being edited wins, so it is
scoped by directory rather than nested inside the work taxonomy at all.
[atlan.com guide](https://atlan.com/know/how-to-write-agents-md/). It matters to
this investigation mainly as a _negative case_: it is the piece of the
"agent-native" landscape that is deliberately **not** a work-item format, and
confirms that project standing/constraints belong in a separate document from
task state.

## GitHub Copilot coding agent (issue assignment)

**What it is.** A cloud-hosted SWE agent inside GitHub, triggered by assigning a
GitHub Issue to "Copilot" exactly as you'd assign a teammate. Confirmed current
via GitHub's own docs and blog as of 2026.
[GitHub Docs: kick off a task](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/kick-off-a-task),
[GitHub Blog: assigning issues](https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/).

**Unit handed to the agent.** A GitHub **Issue** [ENTITY] — the existing GitHub
issue-tracking unit, unmodified in format. No new task schema; the "agent-
native" part is entirely in the _workflow_, not the file format.

**Fields.** Whatever a GitHub Issue already carries (title, body, labels,
assignee) — Copilot itself derives a checklist from the issue body rather than
requiring one.

**Spec → tasks relationship / state write-back.** Copilot reads the issue,
"breaks it down into a checklist of tasks," and **writes that checklist into the
pull request description**, not back onto the issue — so the PR becomes the live
task list, checked off commit by commit ("As it completes each task, Copilot
checks it off and pushes commits to the branch"). The issue stays a static
**[ENTITY]**; the PR description is the **[VIEW]**/working checklist that
mutates. On completion, Copilot adds the human as reviewer.
[GitHub Blog: meet the new coding agent](https://github.blog/news-insights/product-news/github-copilot-meet-the-new-coding-agent/),
[GitHub Docs: cloud agent](https://docs.github.com/en/copilot/concepts/agents/cloud-agent/about-cloud-agent).

**Human review.** The existing PR review flow — comments tagging `@copilot`
drive iteration, and merge is the closure event. No bespoke UI; Copilot reuses
GitHub's own review surface entirely.
[GitHub Blog](https://github.blog/ai-and-ml/github-copilot/assigning-and-completing-issues-with-coding-agent-in-github-copilot/).

## Linear for Agents

**What it is.** Linear's own agent-delegation feature, with "Coding sessions"
(launched June 11, 2026) that start a Claude Code or Codex session directly from
a delegated issue. Confirmed current via Linear's own docs/changelog.
[linear.app/docs/agents-in-linear](https://linear.app/docs/agents-in-linear),
[Coding sessions changelog](https://linear.app/changelog/2026-06-11-coding-sessions).

**Unit handed to the agent.** A Linear **Issue** [ENTITY] — again, the
pre-existing PM unit, not a new agent-specific format.

**Delegation model — a distinctive ownership split.** When an issue is delegated
to an agent, **the human stays the primary assignee**; the agent is added as a
**contributor**, not the assignee. "The assignee remains responsible for the
work, while the agent contributes on their behalf." This is a state/ownership
pattern not seen in the other systems surveyed — most treat the agent as a full
substitute assignee (Copilot) or an anonymous worker pulling from a ready queue
(beads).
[linear.app/docs/assigning-issues](https://linear.app/docs/assigning-issues),
[linear.app/developers/agents](https://linear.app/developers/agents).

**Mechanics.** Delegation fires an `AgentSessionEvent` webhook carrying an
`agentSession` object (issue, comment, context) to the agent runtime; state
write-back happens through the same webhook/API surface Linear uses for any
issue update — no separate file format, since Linear is not file-based.
[linear.app/developers/agents](https://linear.app/developers/agents).

## Devin (Cognition)

**What it is.** A cloud-hosted autonomous SWE agent product, confirmed active in
2026 with its own docs/release notes.
[docs.devin.ai](https://docs.devin.ai/release-notes/2026).

**Unit handed to the agent.** A **session** — a scoped, timed task the human
prompts, optionally starting in "Ask mode" (planning) before switching to "Agent
mode" (execution). No standard on-disk plan-file format was found in Devin's own
docs for this pass (unlike Spec Kit/Kiro's `plan.md`); planning output surfaces
as chat/IDE state during the session rather than a committed artifact.
**Unconfirmed** whether Devin persists a plan file into the repo by default.
[ChatPRD: Devin workflows](https://www.chatprd.ai/how-i-ai/workflows/tool/devin),
[Fastio: Devin session tools](https://fast.io/resources/devin-session-tools-guide/).

**Sizing guidance.** Cognition's own advice: tasks of roughly three hours or
less are the right size for a single Devin session; larger work should be split
into multiple focused sessions — a practitioner-level sizing heuristic distinct
from all the file-based tools above, which size a task by "one deliverable"
rather than by a time budget.
[ChatPRD: Devin workflows](https://www.chatprd.ai/how-i-ai/workflows/tool/devin).

**State write-back / review.** Devin's output is a pull request, reviewed the
normal git-hosting way; AGENTS.md is one of the context files Devin reads
natively per the AGENTS.md adoption list above.

## Obsidian Tasks (markdown-frontmatter / inline task formats)

**What it is.** A community plugin (not agent-specific) that represents tasks as
plain markdown checkboxes with **emoji-coded inline metadata** rather than YAML
frontmatter — included here as the frontmatter-adjacent alternative the brief
asked to check. Confirmed current.
[Tasks Emoji Format, Obsidian Publish](https://publish.obsidian.md/tasks/Reference/Task+Formats/Tasks+Emoji+Format).

**Format.** `- [ ] Task description 📅 2023-04-16 ⏫ 🔁 every day 🏁 keep` — due
date (📅), scheduled (⏳), start (🛫), done (✅), cancelled (❌), priority
(🔺⏫🔼🔽⏬), recurrence (🔁), completion handling (🏁). All metadata lives
inline in the checkbox line itself, not in a frontmatter block — the task line
_is_ the entity, and status is the checkbox state (`[ ]`/`[x]`) plus the
done-date emoji, both **[STATE]** encoded at the character level rather than as
a structured field.
[Tasks Emoji Format](https://publish.obsidian.md/tasks/Reference/Task+Formats/Tasks+Emoji+Format).
No coding-agent adoption of this specific format was found — it is
human/Obsidian-native, not agent-native; included per the brief but not part of
the agent-tool comparison table below. todo.txt-style formats were searched for
but no 2025–2026 coding-agent adoption was found either; **unconfirmed / likely
not in active agent use**.

## Synthesis

### Entity / State / View, sorted

- **[ENTITY]** — things with independent identity and a durable record: Spec
  Kit's `spec.md`/`plan.md` (one per feature, file-identified by directory);
  Kiro's `requirements.md`/`design.md`; Backlog.md's task file (frontmatter
  `id`); Beads' issue (hash ID, hierarchical for parent/child); Task Master's
  task/subtask (`id` in both `tasks.json` and its own file); GitHub Issues and
  Linear Issues (pre-existing entities, reused rather than reinvented for agent
  work).
- **[STATE]** — a field recording progress, always cheap to flip: Backlog.md's
  `status` frontmatter key; Beads' `status`/`priority`; Task Master's `status`;
  Spec Kit's and Copilot's checkbox-ticked-in-place; Obsidian Tasks' checkbox +
  done-date emoji. Every system in this survey keeps state as small,
  mechanically-writable data — none put narrative state changes inline in prose
  the way a human status update might.
- **[VIEW]** — a grouping or lens derived from entities + state, not itself a
  source of truth: Spec Kit's per-branch directory; Backlog.md's Kanban board
  and `bd ready`-style queries; Copilot's PR-description checklist (a _view_
  onto the issue, re-derived, not the issue itself); AGENTS.md (a view onto the
  codebase, not onto work at all).

**The one genuine state-as-folder case: Backlog.md.** Its `status` field and its
folder placement (`backlog/tasks/` vs `backlog/drafts/` vs `backlog/archive/`)
are kept in sync by the tool — the folder is a **materialized, tool-maintained
view of the field**, not an independent encoding. Every other system in the
survey keeps state purely as a field (frontmatter, DB column, or checkbox) and
derives any folder/board grouping from it at read time. This matters directly
for project-docs' current design, where `backlog/` _is_ a folder-as-state for
one type (a "promoted" backlog item physically moves to `projects/`) —
Backlog.md is the closest external precedent for that pattern, and it treats the
folder move as a side effect the CLI performs automatically on a field write,
never as something authored by hand. No system in this survey uses folder
location as the _only_ record of state with no accompanying field —
folder-as-state is consistently a synced mirror, not a replacement.

### What the agent-native tools agree on

1. **A task is the smallest unit an agent is handed, and it is deliberately
   small** — one deliverable, one PR-checklist line, one file. None of the
   agent-native tools hand an agent a "story" or "epic" directly; those are
   grouping constructs a task points up to (via `parent`, hierarchical ID, or a
   plan file), never units of execution.
2. **Dependencies are a first-class field, not prose.** Spec Kit (`[P]`
   ordering), Backlog.md (`dependencies`), Beads (blocker edges gating
   readiness), Task Master (`dependencies`) all make "what blocks this" a
   structured, queryable field — this is the part of the landscape most clearly
   built _for_ agents rather than inherited from human PM tools: an agent needs
   to mechanically ask "what can I start now," which `bd ready` answers
   directly.
3. **Acceptance criteria travel with the task, in some form, everywhere** — EARS
   notation (Kiro), an in-body checklist (Backlog.md), `testStrategy` (Task
   Master), gate/completeness checklists (Spec Kit). No system leaves "done"
   undefined.
4. **State write-back is mechanical and frequent**, not a periodic status
   meeting: a checkbox, a CLI flag, an atomic claim transaction, or an
   auto-written JSON field — always small, structured, and safe to write many
   times a session.
5. **A spec/plan document is consistently upstream of tasks, and consistently a
   separate file from the tasks it produces** — this directly answers one of the
   investigation's open questions: in every agent-native tool surveyed (Spec
   Kit, Kiro, Task Master), the proposal/plan is a **document an entity points
   to or is generated from**, not the unit of work itself. Tasks are the work;
   specs and plans are inputs held alongside them.

### Where they differ

1. **Markdown-as-record vs. markdown-as-export.** Backlog.md, Spec Kit, Kiro,
   and Task Master's per-task files treat the markdown/JSON file as the
   authoritative record. Beads is the outlier: it treats flat files
   (`issues.jsonl`) as a lossy export of a real database (Dolt), explicitly not
   the source of truth. This is a real fork in the design space, not a detail —
   it trades git-diffability for atomic multi-writer transactions and query
   power.
2. **Whether the agent gets a new format at all.** Copilot and Linear hand the
   agent the _pre-existing_ PM unit (a GitHub/Linear Issue) unchanged; Spec
   Kit/Kiro/Backlog.md/Task Master/Beads all invent an agent-specific file or
   record format. The SaaS tools' innovation is in the _assignment and
   write-back workflow_ (webhook, PR-description checklist, contributor role),
   not in a new task schema.
3. **Ownership model when an agent works an issue.** Linear's contributor model
   (human stays assignee, agent adds work) is unique among tools surveyed;
   Copilot and beads both effectively make the agent the sole worker of record
   for the duration (Copilot as assignee-equivalent, beads via atomic claim).
4. **How tightly the spec stays "live."** Kiro keeps the full requirements/
   design context loaded for every task interaction. Task Master consumes the
   PRD once, at generation time, and does not re-consult it. Spec Kit sits
   between: plan and tasks are separate files an agent can re-read but nothing
   forces it to.
5. **Session vs. file as the unit of accounting.** Devin's unit is a time-boxed
   _session_ (~3 hours as a sizing heuristic) with no committed plan-file
   convention found; every other agent-native tool in this survey sizes and
   records work as a _file_, independent of how long it took.

### Agent-specific ideas vs. classic PM renamed

**Genuinely new, driven by agents specifically:**

- Machine-queryable dependency/readiness graphs as the primary retrieval
  mechanism (`bd ready`) rather than a human scanning a board.
- Structured, testable acceptance-criteria grammars meant to be parsed, not just
  read (EARS notation in Kiro).
- Parallel-execution markers on tasks (Spec Kit's `[P]`) — a concept with no
  real analog in human sprint planning, because humans don't fan out identical
  workers.
- Atomic claim semantics to prevent two agents racing on the same task (beads).
- The PR-description-as-live-checklist pattern (Copilot) — reusing a review
  artifact as the working task list, so state lives where the reviewer already
  looks.
- The AGENTS.md convention itself: a context file with no work-item semantics at
  all, existing purely because agents (unlike humans who absorb project culture
  by osmosis) need conventions stated explicitly and in a predictable,
  nearest-file-wins location.

**Classic PM concepts, renamed or lightly adapted:**

- Task/subtask/dependency/priority/status (Task Master, Backlog.md) — this is
  Jira/Linear's issue model, minus the human fields (assignee-as-person, due
  date, estimate) that don't matter to an agent, restated as a file. Backlog.md
  itself frames its Kanban board and milestones in explicitly human-familiar
  terms.
- Spec → plan → tasks (Spec Kit, Kiro) is PRD → design doc → work breakdown
  structure, formalized as files instead of wiki pages — the sequence itself
  predates agents by decades; what's new is that the files are the interface an
  agent consumes directly rather than a document a human reads before writing
  tickets by hand.
- Delegating an issue to a worker who is a "contributor" not the "assignee"
  (Linear) is a reframing of how a tech lead assigns a pairing partner or
  contractor, not a new concept.
