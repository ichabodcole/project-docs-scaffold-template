# Re-pin to 9.2.0 and plugin 4.2.0 — 2026-09-29

Part of [Story-loom migration](../../../cycles/2026-09-story-loom-migration.md).

## Context

The cycle's thirteen items landed on develop, and scaffold 9.2.0 was released
from them (PR #183). By the rule this cycle wrote into the migrations playbook,
the newest migration must then be re-pinned to the new release, and the plugin
carrying it released. A plugin can only pin a tag that exists, so the re-pin
follows the scaffold release. Last cycle that commit cut a content-free scaffold
release (9.1.0). Cole chose to prevent that this time.

## What Happened

Three commits, landed by fast-forward so each keeps its type:

- **`chore(release)`:** `release-please-config.json` gains
  `"exclude-paths": ["plugins", "dist"]`, so a commit touching only those paths
  doesn't count toward the scaffold.
- **`docs(playbooks)`:** Step 14 of the migrations playbook now lists everything
  this re-pin touched, and says to run the whole suite, because a new lint rule
  in the release can stop the migration's verify phase.
- **`feat(project-docs)`:** the v3.0 migration installs 9.2.0. `OWNED_RELEASES`
  gained six keys (its test failed until they were added), plugin `project-docs`
  went to 4.2.0 with its Version History, and the guide's stop step names
  `NO OUTCOME`.

  9.2.0's `NO OUTCOME` rule runs in the migration's verify phase, so an adopter
  tree with a closed cycle whose Outcome is unwritten now stops there, with a
  worklist, before its markers move. It caught the test fixture's own closed
  cycle.

the 9.2.0-pinned run stopped at the same 249 problems as the 9.1.0-pinned run,
with no `NO OUTCOME`. It ran typecheck and the full gate (1988 pass). Verdict:
**Ready to merge: Yes, by fast-forward**.
