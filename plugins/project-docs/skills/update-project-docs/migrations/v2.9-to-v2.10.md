# Migration: v2.9 → v2.10

## Summary

v2.10 delivers the fixes the first consumer's feedback produced (plugin 3.11.0)
to a project that already has the layer. The owned files — `scripts/pdocs/` and
`docs/SCHEMA.md` — ship inside the scaffold payload and reach a project only
through a migration, so a tree adopted at 8.0.0 is still running the lint that
hid a real page named `templates.md`. This migration replaces those files, and
it is the **first migration to reconcile the seeded templates**: for every
template the scaffold ships it asks `docs/.pdocs-seed.json` whether you have
touched yours, updates the ones you have not, and names the ones it leaves
alone.

**What changes in your tree:** `scripts/pdocs/` and `docs/SCHEMA.md` are
replaced; each template you have not edited since it was recorded is updated to
the scaffold's (one moves at this release: `docs/playbooks/TEMPLATE.md`), a
template new to the release is installed, and `docs/.pdocs-seed.json` is
rewritten with those hashes; Prettier is run over the templates the run wrote
(skippable); both version markers are set when the scaffold's release is ahead
of yours. No document you wrote is touched, and no template you edited, deleted
or never had recorded is written.

## This migration is a script

One command does the whole migration. Every phase verifies itself, and any
failure stops the run with a non-zero exit and a named reason — including
failures the script did not anticipate.

**Why, in two sentences you can check yourself.** A guard computed in one shell
block and consumed in the next runs in a **different process**, so it protects
nothing. A check whose only output is an echoed string cannot fail a run. One
process and real exit codes make both impossible rather than discouraged.

## What's New

The 3.11.0 fixes, in `scripts/pdocs/` and the contract: a template is an exact
name shape (`TEMPLATE.md`, `TEMPLATE-<variant>.md`,
`YYYY-MM-DD-TEMPLATE-<type>.md`, `<name>.template.md`, anything under
`TEMPLATES/`), never a substring — so a real page called `templates.md` is
linted like the page beside it; `seed.ts` and the lint decide "template" by one
rule, and a recorded path stays a template whatever it is called;
`pdocs check --format json` names what it skipped as templates under
`data.templates`; `docs/SCHEMA.md`'s Seeded row names the five shapes and the
one exception a migration makes to `.project-docs.json` being yours; and
`docs/playbooks/TEMPLATE.md` is Prettier-clean under default options. The
codemod and hook fixes from the same release (#164, #165, #168, #169) live in
the plugin and the v2.6 migration, not in your tree, and need no delivery.

## What Moved / What's Removed

Nothing, in either case.

## Before you run it

**Exclude `scripts/pdocs/` from every formatter and linter the project runs** —
`scripts/pdocs/` in `.prettierignore`, `"!!scripts/pdocs"` in Biome's
`files.includes`, an `ignores` entry in the ESLint config. Cover every tool the
project has, not only the one in its pre-commit hook: Prettier and Biome each
reformat the directory on their own. Commit the exclusion before the run.

`scripts/pdocs/` is **owned**. Every migration's refresh copies the scaffold's
bytes over it — it does not keep your version of a file — so a formatter that
reads the directory starts a loop: the refresh restores the scaffold's bytes,
your formatter rewrites them on the next commit, and every later migration shows
a diff neither side intended. Excluding the directory ends the loop, and nothing
is lost by it: these files are not yours to edit.

Do it first, because a formatter in a pre-commit hook gets there before you do.
The run refreshes the layer, the commit's hook reformats it, and if that commit
then fails for any reason the layer is left modified and uncommitted — and a
re-run stops on `N path(s) this run would write have uncommitted changes`.
`--force` is the right answer to that stop, since the changes are your
formatter's and not yours; the exclusion is what keeps you from meeting it. If
your formatter has already been over the directory, phase 3 says so: it reports
the files it writes, and those are the ones that had drifted.

`tsc` is the exception: the layer typechecks under a Bun-shaped `tsconfig`
(`allowImportingTsExtensions`, `types: ["bun"]`) with `strict` and
`noUncheckedIndexedAccess` on, so a config of that shape needs no exclusion. A
conventional one does — it fails on the `.ts` import specifiers alone.

## Run it

```bash
cd <your project root>              # the directory holding .project-docs.json
SKILL_DIR=<the update-project-docs skill directory>
bun "$SKILL_DIR/migrations/scripts/migrate-v2.9-to-v2.10.ts" --dry-run
```

Set `SKILL_DIR` in the **same** block you use it in, or paste the literal path —
a shell variable does not survive into a separate command. An agent that loaded
`update-project-docs` has the directory as its "Base directory for this skill";
otherwise it is two levels above this file. `bun` must be on PATH: the script
runs under it, and so does the gate it refreshes.

The dry run generates the scaffold, changes nothing in your project, and prints
what each phase would do. A run without `--scaffold-dir` lets cookiecutter write
outside `--root`: its clone cache in `~/.cookiecutters/` and a replay file in
`~/.cookiecutter_replay/`, as the earlier scripts' do. **Three things to read in
it:**

- **The reconcile verdicts.** One line per template the scaffold ships, each
  carrying its verdict: `would update` (recorded and untouched — the scaffold's
  moved and yours will follow), `already at the scaffold's bytes` (nothing to
  write), `would install` (new in this release), or `would keep` with one of
  three reasons — `keep-modified` (you edited it since it was recorded),
  `keep-unknown` (on disk but never recorded; unknown is not permission),
  `keep-deleted` (recorded, and you deleted it; deleting is an edit). A recorded
  path the scaffold no longer ships is named and left as it is. On a tree
  adopted at 8.0.0 and untouched since, expect one `would update`
  (`docs/playbooks/TEMPLATE.md`) and eighteen `already at the scaffold's bytes`.
  A `keep-modified` you do not remember making is worth a look before the real
  run: it is a template that will stop receiving the scaffold's changes.
- **The verify plan, and the preflight's baseline.** Phase 1 prints what
  `pdocs check` says under the CLI you have today. Phase 5 will run it again
  under the refreshed one, and the refreshed lint may find problems the older
  one hid — see [After the script](#after-the-script). A baseline that is
  already red means the real run will stop at phase 5 whatever this migration
  does; work that first, or run with the gate off.
- **The markers.** `would set docs/README.md from X to Y` and the same for
  `.project-docs.json` when the scaffold's release is ahead of yours;
  `already at` when it is not. Both, or neither.

Then, setting `SKILL_DIR` again — it is a separate command:

```bash
SKILL_DIR=<the update-project-docs skill directory>
bun "$SKILL_DIR/migrations/scripts/migrate-v2.9-to-v2.10.ts"
```

Commit the result, `docs/.pdocs-seed.json` included.

**If phase 2 stops saying the scaffold is older than this migration requires.**
The script fetches the scaffold from the published template, and this migration
ships with the plugin; the two are at different points whenever `develop` is
ahead of the last release. Phase 2 verifies, in both modes and before anything
is written, that the scaffold's `scripts/pdocs/lint/rules.ts` carries `isSeeded`
and its `docs/SCHEMA.md` names the exact template shapes, and stops naming what
is missing. The remedy is the one below: generate the scaffold from a ref that
has it, and pass it with `--scaffold-dir`.

**If your tree carries a fix that is on the template's `develop` and not yet
released, a plain run reverts it.** Without `--scaffold-dir` the script fetches
the scaffold from the published template —
`gh:ichabodcole/project-docs-scaffold-template`, its `main` — and phase 3 copies
that scaffold's `scripts/pdocs/` and `docs/SCHEMA.md` over yours, keeping
nothing of yours. If you took the layer from `develop`, or copied a fixed file
out of it, `main` is behind your tree and the run puts the older bytes back.
Phase 2 cannot see that: it checks the scaffold is new enough for this
migration, not that it is as new as your tree. Probe first, with the commit that
carries the fix:

```bash
(
  T=$(mktemp -d); trap 'rm -rf "$T"' EXIT
  git clone --quiet --bare https://github.com/ichabodcole/project-docs-scaffold-template "$T" || { echo "STOP — could not clone the template"; exit 1; }
  git -C "$T" cat-file -e '<sha-of-the-fix>^{commit}' 2>/dev/null || { echo "STOP — the template has no such commit; check the SHA"; exit 1; }
  git -C "$T" merge-base --is-ancestor <sha-of-the-fix> main || { echo "NOT RELEASED — main lacks it; generate the scaffold from the ref that has it"; exit 1; }
  echo "released — a plain run fetches it"
)
```

The dry run is a second probe: phase 3 names every file under `scripts/pdocs/`
it would write, and a file you know you fixed appearing in that list means the
scaffold is older than your tree.

On `NOT RELEASED`, generate the scaffold from the ref that has the fix and pass
it in — `develop` below, or whichever ref it is. This is the script's own
cookiecutter call with `--checkout` added:

```bash
SKILL_DIR=<the update-project-docs skill directory>
cookiecutter gh:ichabodcole/project-docs-scaffold-template --checkout develop --no-input -o <tmp> 'install_target=New project folder'
bun "$SKILL_DIR/migrations/scripts/migrate-v2.9-to-v2.10.ts" --dry-run --scaffold-dir <tmp>/my-project
```

`<tmp>` is an empty directory you made. `install_target=New project folder` is
load-bearing: `--no-input` otherwise takes the first choice, the
current-directory install, which unpacks the payload into `<tmp>` itself and
prints next steps for a project you are not creating. With it, cookiecutter
generates exactly one folder inside `<tmp>` — `my-project`, the default slug —
and that folder is the scaffold root. The script refuses a `--scaffold-dir` that
lacks `docs/SCHEMA.md` or `scripts/pdocs/`, so a wrong path stops the run rather
than copying from nowhere. A scaffold generated from `develop` still carries the
last release's `docs_version`, so both markers end where a plain run would have
put them.

Read the dry run, run it again without `--dry-run`, then confirm the layer is
the one you generated — this prints nothing when it is:

```bash
diff -rq scripts/pdocs <tmp>/my-project/scripts/pdocs
```

Or wait for the release, and run without the flag.

### Options

| Flag                 | When you need it                                                                                                                                                                                                                                  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--root <path>`      | The project to migrate. Defaults to the current directory.                                                                                                                                                                                        |
| `--dry-run`          | Generate the scaffold, print every verdict and every phase's plan, change nothing in the project. The scaffold is removed afterwards.                                                                                                             |
| `--scaffold-dir <p>` | Use a scaffold you already generated instead of fetching one — the remedy when the published template is behind this migration or behind your tree (above). Skips the network and the `cookiecutter` check. `--scaffold` is accepted as an alias. |
| `--skip-format`      | Do not run Prettier over the templates this run writes. **Required** if your project has no `npx` or does not use Prettier — otherwise the preflight stops rather than record hashes your own formatter would invalidate on commit.               |
| `--force`            | Write over uncommitted changes in the paths this run touches. Without it the preflight stops on them and names each one.                                                                                                                          |

Exit codes: `0` success · `1` the migration could not complete · `2` bad
invocation.

## What it does, phase by phase

1. **Preflight** — confirms this is a v2.9 tree: `.project-docs.json`,
   `docs/SCHEMA.md`, `scripts/pdocs/cli.ts` and `docs/.pdocs-seed.json` all
   present. A missing one stops the run and names the migration that owns it
   (`v2.6-to-v2.7` for the first three, `v2.8-to-v2.9` for the manifest);
   migrations run in sequence. Requires `bun` on PATH, `cookiecutter` (unless
   `--scaffold-dir`) and `npx` (unless `--skip-format`). Reads `git status`:
   **dirt in a path this run will write stops the run** — `scripts/pdocs/`,
   `docs/SCHEMA.md`, `docs/.pdocs-seed.json`, and every recorded template whose
   bytes still match its record, since those are the ones phase 4 writes over —
   naming each; commit or stash, or pass `--force`. Dirt anywhere else is
   reported and the run goes on. Then runs `pdocs check` once under the CLI you
   have today and reports the result as the **baseline** phase 5 compares
   against; a CLI that cannot answer is a note, not a stop.
2. **Scaffold** — generates the current template into a private temp directory,
   never into your project, and verifies it is new enough for what phase 3
   installs: `scripts/pdocs/lint/rules.ts` carrying `isSeeded`, `docs/SCHEMA.md`
   naming the exact template shapes, and a parsable `docs_version` — the release
   both markers end at. A scaffold missing any of these stops the run here, in a
   dry run too, naming what is missing and how to supply a newer scaffold. The
   temp directory is removed however the run ends.
3. **Refresh the owned files** — `scripts/pdocs/` (**owned**: replaced; the copy
   merges, so a file of your own beside the CLI survives, and so would a file a
   later release removed) and `docs/SCHEMA.md` (**owned**: replaced). Each
   reports refreshed, replaced, or already identical to the scaffold's. The
   markers phase 2 verified on the source are read back from the installed files
   by the end-of-run check.
4. **Reconcile the seeded templates** — a manifest key that is not a path inside
   the docs root (a hand-edited `../x.md`) is named and dropped from the record,
   as `seed.ts`'s own writer refuses it. Then, for every template the scaffold
   ships (**seeded**: negotiated by hash), the verdict against
   `docs/.pdocs-seed.json` through the logic copied from
   `scripts/pdocs/seed.ts`: `update` writes the scaffold's bytes (or reports
   `already at the scaffold's bytes`), `install` writes a template you never
   had, and `keep-modified`, `keep-unknown` and `keep-deleted` are named and
   left alone. A recorded path the scaffold no longer ships is named and its
   record kept. Then Prettier over the templates this run wrote — **before**
   recording, never after, and only over those — and a formatter that fails
   stops the run before anything is recorded. Then the record: the written and
   the identical templates get the hash of the bytes on disk now, every other
   entry keeps the hash it had, a `keep-unknown` is never recorded (recording it
   would read as "untouched" next time), and the manifest's `version` becomes
   the scaffold's release. The file is written only if it changed, in its own
   indent. A scaffold that ships no templates stops the run.
5. **Verify** — runs `pdocs check` under the refreshed CLI. Exit 0 continues
   (with the problem count noted when `lint.adopting` is true). Anything else
   **stops the run with exit 1, after the refresh and before the markers move**:
   the message says how many problems the refreshed lint reports and, against
   the baseline's problem lines, which are new to it, which the older lint no
   longer reports and which are unchanged; that the refresh stays — rolling it
   back would reinstall the lint that hid them — that the markers were not
   moved, that `pdocs report` is the worklist, and that re-running is safe. A
   CLI that prints nothing the script can read stops the run too.
6. **Version markers** — sets `docs_version` in `docs/README.md` and `version`
   in `.project-docs.json` to the scaffold's release, reporting each separately
   and writing each only when the value moves. `.project-docs.json` is
   **theirs**, so only that one value is written: the top-level `"version"` is
   patched in the file's own text — indent, array style and every other byte
   kept — and the result is parsed and checked against the intended object
   before it is written. Only when there is no top-level `"version"` to patch
   does the phase re-serialise the file, in its own indent, and the phase line
   says so. A README with no `docs_version` line is a `·`, and the end-of-run
   check then fails the run.
7. **Cleanup** — removes the generated scaffold. A supplied `--scaffold-dir` is
   left in place.

**Then the script checks its own work.** Before exiting 0 it re-reads the tree
and confirms what the phase ordering guarantees: the installed `rules.ts`
carries `isSeeded` and the installed `SCHEMA.md` names the exact shapes; the
manifest parses, is at the scaffold's release, every template this run recorded
still matches its record (the format-before-record ordering), and no template
the scaffold ships is left neither on disk nor recorded; both markers are at the
scaffold's release; `pdocs check` exits 0 on the result; and the generated
scaffold is gone. Any line that does not hold fails the run and names the phase
responsible, so the ordering is enforced rather than merely intended.

## After the script

Two things the script leaves to you, in this order.

### 1. If phase 5 went red, work the problems and re-run

The refreshed lint judges pages the older one skipped. Story-loom's case is the
model: a real specification named `templates.md`, hidden by the old substring
rule, has no frontmatter and no catalog line, and the new lint reports both.
That is the refresh working, and the script does not roll it back. The tree is
not at v2.10 until the check passes, which is why the markers stay where they
were.

Work the worklist —

```bash
bun scripts/pdocs/cli.ts report --format text
```

— then commit and re-run the migration. Every phase finds its work done
(`already identical`, `unchanged`, every template
`already at the scaffold's bytes` or kept), the check passes, the markers move,
and the run exits 0. It sits here rather than earlier because nothing before
this point can be judged until the lint that judges it is installed.

### 2. Commit the result, `docs/.pdocs-seed.json` included

The manifest is the record the next migration reads. A manifest that never
reaches the repository cannot be read next time, and the templates this run
updated read as your edits from then on. Commit it with the owned files and the
templates, in one commit, so the diff is "the release arrived" and nothing else.

## What it cannot check

- **That the result is committed**, and committed alone. The script leaves the
  tree dirty on purpose; the commit is yours.
- **That a `keep-modified` is an edit you meant.** The script can tell that the
  bytes differ from what was recorded, not why. If the record was wrong from the
  start — the v2.9 adoption ran before a reformat — that template will not be
  updated by this or any later migration until you make its bytes the baseline
  again (`migrate-v2.8-to-v2.9.ts --re-adopt` rewrites the whole record; the
  v2.9 guide's "If you run it twice" says when that is safe).
- **That a `keep-unknown` should stay yours.** A template the manifest never
  recorded is left alone; the v2.9 adoption's `--re-adopt` records it if you
  want the scaffold to update it from now on.
- **That the problems phase 5 found are worked correctly.** It counts them; the
  `description` on a page it found bare is one sentence a person has to mean.
- **Your own pre-commit hook.** The templates this run writes are formatted with
  your Prettier before their hashes are recorded, so a diff on them from a
  Prettier-based hook means your options differ from the defaults the templates
  ship in; run your formatter over them by hand, then re-run this migration — it
  re-records nothing, and its end-of-run check confirms every recorded hash
  still holds. `scripts/pdocs/` is **owned**, replaced wholesale on upgrade;
  exclude it from your formatter rather than adopting it, as
  `update-project-docs` § Step 7 describes.

## What it does not do

- **It does not re-adopt.** The v2.9 migration recorded your templates as they
  stood; this one compares against that record and never rewrites an entry it
  did not update. A stale or missing entry is `keep-modified` or `keep-unknown`,
  named in the output, and left for you to decide.
- **It does not touch a `keep-*` file** — not its bytes, and not its record. A
  `keep-deleted` stays deleted and stays recorded, so the next migration keeps
  it deleted too.
- **It does not write `description`**, or any field, on any page. The verify
  phase reports; the backfill is yours.
- **It does not roll back the refresh when the check goes red.** The refreshed
  lint is the correct one; the tree is what has to change.

## If you run it twice

Re-running is safe. Commit first — a re-run over the uncommitted result stops in
the preflight, naming every path it would write, because the first run's changes
cannot be told apart from yours. Then every phase reports what it finds already
done and continues: `scripts/pdocs/ already identical to the scaffold's`,
`docs/SCHEMA.md already identical`, every template
`already at the scaffold's bytes` or kept with the same reason,
`nothing was written, so nothing to format`, `docs/.pdocs-seed.json unchanged`,
both markers `already at`. The tree is byte-identical afterwards.

A re-run after phase 5 stopped is the same command with no flag: the refresh is
found done, the record is found current, and the check is asked again.

## Verification

The script checks all of this itself and stops on any failure, so this is what
to look for in its output rather than commands to run.

- [ ] `✓ v2.9 tree at <root>, docsRoot docs/, docs_version <yours>, .project-docs.json version "<yours>"`
- [ ] `✓ git tree clean` — or `· working tree is dirty (N path(s))` for dirt in
      paths the run does not write; dirt in one it does write stops the run
      before this, naming the path, unless you passed `--force`
- [ ] ``· `pdocs check` under the installed CLI: clean — the baseline …`` — or
      `exit N, M problem(s)`, in which case expect phase 5 to stop unless the
      gate is off
- [ ] `✓ generated at <path>` (or `✓ using <path>` with `--scaffold-dir`), then
      `✓ release <X>, carrying what the refresh installs (…)`
- [ ] `✓ scripts/pdocs/ refreshed (N file(s) written; …)` and
      `✓ docs/SCHEMA.md replaced (owned)` — on a re-run, both read
      `✓ … already identical to the scaffold's`
- [ ] one line per template, each `✓ updated`, `✓ installed`,
      `· … already at the scaffold's bytes`, or `· kept … — keep-<reason>: …`
- [ ] `✓ formatted N written template(s) with your Prettier — before recording,     never after`
      — unless you passed `--skip-format` (`· formatting skipped`) or nothing
      was written (`· nothing was written, so nothing to format`)
- [ ] `✓ docs/.pdocs-seed.json written: N template(s) recorded at version <X>,     M entries — commit it with the rest`
      — or `✓ … unchanged (M entries,     version <X>)`
- [ ] `✓ N template(s) in the scaffold: U updated, I already at the scaffold's     bytes, J installed, K kept (modified), L kept (unknown), D kept (deleted)`
- [ ] `✓ pdocs check: clean (exit 0)` — or, with the gate off,
      `✓ pdocs check:     exit 0 — N problem(s) reported, and lint.adopting is true …`.
      A ``STOPPED: `pdocs check` exits N on the refreshed tree`` here is
      [After the script](#after-the-script), not a defect
- [ ] `✓ docs/README.md set to <X>` and
      `✓ .project-docs.json set to <X> — that     one key; every other byte as it was`
      — or both `already at <X>` when the scaffold's release is yours
- [ ] `✓ generated scaffold removed` (or
      `· scaffold was supplied with     --scaffold-dir — left in place`)
- [ ] `Migration complete. N template(s) reconciled, M recorded; the owned files     are at release <X>.`
      and **exit 0.** The exit code is the check; the lines above tell you which
      phase produced it
- [ ] `git status` shows the migration's changes and nothing else, and they are
      committed, `docs/.pdocs-seed.json` included. **The script cannot check
      this.**
