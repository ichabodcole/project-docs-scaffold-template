# Migration: v2.10 → v3.0

## Summary

v3.0 is the first major structural break in this series. It ships two changes as
one release. **Work Taxonomy** replaces the ad hoc work folders with three
entities — a **feature** (`features/<slug>/feature.md`), a **work item**
(`items/<slug>.md`, or `items/<slug>/item.md` once it owns documents) and a
**cycle** — whose documents live with them, whose relationships are fields, and
whose states come from one grouped vocabulary. **Guidance Lifecycle** retires
`memory` and `lesson`, reshapes playbooks to Goal · Steps · Verification, and
seeds `docs/STYLE.md`.

This is the first migration that **moves documents you wrote**. `docs/SCHEMA.md`
§ "Who owns which file" allows a major migration to move a document and rewrite
its frontmatter and its links. It never rewrites your prose, never deletes a
document, and names every move it makes. This one does exactly that.

**What changes in your tree:** every document in `backlog/`, `fragments/`,
`investigations/`, `reports/` and `projects/` (and their `_archive/`) moves to
`features/` or `items/` with its frontmatter rewritten; the entity files a
research item or a born item needs are created; every link to a moved document —
in `docs/` and in every tracked Markdown file outside it — is respelled;
`scope:` leaves each cycle and becomes `cycle:` on its items; the owned files
(`scripts/pdocs/`, `docs/SCHEMA.md`, `docs/README.md`, `docs/AGENTS.md`,
`docs/CLAUDE.md`, the category READMEs) are replaced and the retired folders'
READMEs removed; the `lint` keys of `.project-docs.json` are patched in the
file's own text; the templates move to `docs/TEMPLATES/` with their seed
records, the retired ones are removed while you have not edited them,
`docs/STYLE.md` is installed, and `docs/.pdocs-seed.json` is rewritten; both
version markers move once the check passes. `memories/` and `lessons-learned/`
are kept.

The three version numbers this release moves are read by different things:

| Number                 | From → to          | What reads it                                                            |
| ---------------------- | ------------------ | ------------------------------------------------------------------------ |
| Package and scaffold   | `8.1.0` → `9.0.0`  | `docs_version` in `docs/README.md` and `version` in `.project-docs.json` |
| `project-docs` plugin  | `3.13.0` → `4.0.0` | what you update to get the new skills                                    |
| Migration-series label | `v2.10-to-v3.0`    | the name of this guide and its script                                    |

**Behind?** This migration needs a v2.10 tree — `scripts/pdocs/lint/rules.ts`
carrying `isSeeded`. Run `v2.9-to-v2.10` first; its preflight says so if you
skip it.

## This migration is a script

One command does the whole migration. Every phase verifies itself, and any
failure stops the run with a non-zero exit and a named reason — including
failures the script did not anticipate.

**Why, in two sentences you can check yourself.** A guard computed in one shell
block and consumed in the next runs in a **different process**, so it protects
nothing. A check whose only output is an echoed string cannot fail a run. One
process and real exit codes make both impossible rather than discouraged.

## What's New

- **Features** — `features/<slug>/feature.md`, `type: feature`, states
  `backlog · ready · active · review · done · dropped`. A proposal is the
  feature.
- **Work items** — `type: item` with a UUID `id`, a `kind`
  (`task · bug · chore · research`) and the states above plus `triage`.
  `parent`, `cycle`, `scope`, `from`, `blocked_by`, `priority`, `assignee` and
  `released_in` are fields.
- **Owned documents** — plans, sessions, reports, write-ups and artifacts live
  in their feature's or item's folder, typed by position.
- **`pdocs`** — `new item`, `new <type> --owner`, `set`, `promote`, `archive`,
  `view` (backlog, board, ready, feature, cycle, scope, unreleased) and
  `check --against <ref>`.
- **Guidance** — `docs/STYLE.md` (seeded); the playbook template is Goal · Steps
  · Verification.

## What Moved / What's Removed

| From                                              | To                                                                                                                                                                              |
| ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `projects/<x>/` with `proposal.md`                | `features/<x>/`, `proposal.md` → `feature.md`; draft/deferred → backlog, approved → ready (active when `plan.md` is active), implemented → done, withdrawn/superseded → dropped |
| `projects/<x>/` without `proposal.md`             | `items/<x>/` and a created `item.md`: `kind: task`, `done` (or `active` when its plan is), described from its latest session                                                    |
| `backlog/<date>-<slug>.md`                        | `items/<slug>.md`, `kind: task`; open → backlog, done → done, promoted → dropped (named for review), dropped → dropped                                                          |
| `fragments/<date>-<slug>.md`                      | `items/<slug>.md`, `kind: task`; open → triage, promoted/dropped → dropped                                                                                                      |
| `investigations/<date>-<slug>[-investigation].md` | `items/<slug>/write-up.md` (`type: write-up`, no lifecycle) and a created `items/<slug>/item.md` (`kind: research`; active → active, concluded → done)                          |
| `reports/*.md`                                    | the `reports/` of the one research item that links to it or that it links to                                                                                                    |
| `cycles/*.md` `scope:`                            | removed; each backlog entry's item carries `cycle: <cycle>`; a project entry is listed in the cycle's Scope section when it is not already                                      |
| `<folder>/_archive/…`                             | `items/_archive/` or `features/_archive/` when the mapped state is `done` or `dropped`; otherwise the live folder, and the run says so                                          |
| `projects/TEMPLATES/*`, the report template       | `TEMPLATES/`; `PROPOSAL.template.md` → `FEATURE.template.md`                                                                                                                    |

A slug two documents would share keeps its date (`items/2026-01-02-fix.md`). A
document with no frontmatter — legacy archives were never linted — gets one: the
type from its new position, the title from its H1, the description from its
first sentence, `status: stable`,
`generated: { by: unknown, at: <first commit> }`; an entity found in a legacy
archive with no lifecycle is `done`.

**Removed**, and only these: the retired folders' READMEs (owned), each retired
template (`backlog/TEMPLATE.md`, `fragments/TEMPLATE.md`,
`briefs/TEMPLATES/BRIEF.template.md`, the investigation template) **while its
bytes still match what the scaffold recorded**, the `.gitkeep` placeholders of
the emptied `_archive/` folders, and the retired folders once empty. A link to a
removed README or template, or to a retired folder itself, is respelled to its
successor.

## Before you run it

The preflight lists every one of these at once and stops before anything is
written. The dry run stops on them too, so run it first to get the list.

1. **Briefs.** A brief has no successor type. Move each into its owner's
   `artifacts/` — `docs/projects/<slug>/artifacts/`, which moves with the
   project; the run turns its `type` to `artifact` — or delete it. Fix the links
   to it either way: `bun scripts/pdocs/cli.ts backlinks <path>` lists them. The
   preflight suggests the owner when the brief links to exactly one project.
2. **Reports without one owner.** A report goes to the research item linked with
   it. When no investigation links to it (and it links to none), or two do, the
   preflight stops on it. Either leave exactly one link between it and the
   investigation it belongs to, or move it into the owning project's `reports/`
   folder (and fix its inbound links). A repository-level report — a docs
   review, a project summary — belongs to a `kind: chore` item: move it aside
   and file that item after the run.
3. **A retired template you edited**, or a file of your own in a retired folder
   that is not a document (an image, a form of your own). Move it out, or delete
   it.
4. **Your memories and lessons: keep or delete.** See below.
5. **Commit or stash first.** The run leaves its changes uncommitted, and it
   stops on uncommitted edits in `docs/`, `scripts/pdocs/`, `.project-docs.json`
   and any outside file whose links it rewrites.
6. **Exclude `scripts/pdocs/` from your formatters and linters**, as for every
   migration that refreshes the owned files.

### Your memories and lessons: keep or delete

`memory` and `lesson` are retired: nothing creates them any more.

- **Keep** (the default): do nothing. The run keeps `docs/memories/` and
  `docs/lessons-learned/` and declares them, so they stay lintable:

  ```json
  "durable": ["architecture", "specifications", "interaction-design", "playbooks", "lessons-learned", "memories"],
  "types": { "memories": "memory", "lessons-learned": "lesson" }
  ```

- **Delete**: before the run, delete the folders and their `docs/index.md`
  lines, and fix the inbound links `pdocs backlinks` names. The script never
  deletes on your behalf.
- **Fold in**: what a lesson says belongs in the playbook for that kind of work,
  as a Step and a Verification (`docs/playbooks/README.md`).

### Active cycles with project scope

A feature carries no `cycle:`. The run lists each `project/<x>` entry in the
cycle's Scope section and, for an **active** cycle, says so: after the run, file
the items that carry that work with `cycle: <cycle>`.

## Run it

From the project root, with the update-project-docs skill directory as
`SKILL_DIR` in the same block:

```bash
SKILL_DIR=<the update-project-docs skill directory>
bun "$SKILL_DIR/migrations/scripts/migrate-v2.10-to-v3.0.ts" --dry-run
```

Read the plan: every move, every frontmatter rewrite, the link count, every
config key. Then run it without `--dry-run`, read the output, and commit.

The script fetches the scaffold from
`gh:ichabodcole/project-docs-scaffold-template` at the tag
`project-docs-scaffold-template-v9.0.0` — the release it was written against
(each migration runs against its own era's scaffold). Until that release is
published, or to use a checkout, generate the scaffold and pass it:

```bash
SKILL_DIR=<the update-project-docs skill directory>
cookiecutter gh:ichabodcole/project-docs-scaffold-template --checkout develop --no-input -o <tmp> 'install_target=New project folder'
bun "$SKILL_DIR/migrations/scripts/migrate-v2.10-to-v3.0.ts" --dry-run --scaffold-dir <tmp>/my-project
```

`<tmp>` is an empty directory you made. `install_target=New project folder` is
load-bearing: `--no-input` otherwise takes the current-directory install. Phase
2 refuses a scaffold without the 9.0.0 layout, in both modes, before anything is
written.

### Options

| Flag                 | When you need it                                                                                      |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| `--root <path>`      | The project is not the current directory                                                              |
| `--dry-run`          | Always, first: generates the scaffold, prints the plan, changes nothing                               |
| `--scaffold-dir <p>` | Use a scaffold you generated (a project root, not its `docs/`). Skips the network. Alias `--scaffold` |
| `--skip-format`      | The project does not use Prettier: what the run creates is not formatted                              |
| `--force`            | Write over uncommitted changes in the paths the run touches                                           |

Exit codes: `0` the migration completed · `1` it could not (the reason is
printed after `STOPPED:`) · `2` bad invocation.

## What it does, phase by phase

1. **Preflight** — a v2.10 tree (config, `SCHEMA.md`, the CLI, the seed
   manifest, `isSeeded`), `bun`, `cookiecutter` unless `--scaffold-dir`, `npx`
   unless `--skip-format`; builds the whole plan read-only; **stops on every
   judgment step above**; stops on uncommitted edits it would write over; runs
   `pdocs check` under the installed CLI as the baseline.
2. **Scaffold** — generates the template at its tag into a private temp
   directory (or takes `--scaffold-dir`) and stops if it lacks the 9.0.0 layout.
3. **Plan** — prints every move, frontmatter rewrite, template move and removal,
   link count and config key. `--dry-run` stops here.
4. **Refresh** — replaces the owned files (`docs/README.md` keeps its
   `docs_version` until phase 11), installs `features/` and `items/` with their
   READMEs and `_archive/`, and removes the retired READMEs.
5. **Move** — moves every document and writes its new frontmatter; creates the
   research and born items' `item.md`. Stops if a destination exists or a move
   does not land.
6. **Links** — writes the link rewrites in files that did not move (moved files
   were written whole in phase 5), including tracked Markdown outside `docs/`
   and not in `lint.exclude`.
7. **Config** — patches `lint.workbench`, `lint.durable`, `lint.types`,
   `lint.skip` (drops `_archive`: the archive is linted now), `lint.exclude`
   (globs naming moved paths) and `lint.scopes` in the file's own text.
8. **Seeds** — moves the templates and carries their records (`renameRecord`),
   removes untouched retired templates and emptied retired folders, then gives
   every template the scaffold ships a verdict: `update`/`install` write, the
   rest are kept and named; `STYLE.md` is installed.
9. **Format, then record** — Prettier over what this run created or installed
   (never a document of yours), then `docs/.pdocs-seed.json`.
10. **Verify** — stops if any retired folder remains, then runs `pdocs check`.
    Red stops the run here, **after** the moves and **before** the markers.
11. **Version markers** — both, to the scaffold's release.
12. **Cleanup** — removes the generated scaffold. Then the program re-checks its
    own invariants.

## After the script

### 1. If phase 10 went red, work the problems and re-run

The legacy archives were never linted, so their old broken links surface now
(`MISSING FILE`), and a brief or report you moved by hand leaves links to fix.
The worklist is `bun scripts/pdocs/cli.ts report --format text`. The moves stay;
re-running the same command finds every phase done and passes once the check
does.

### 2. Declare your scopes, and file what the run named

Add the names `scope:` may take to `lint.scopes`. File the items the run named
for active cycles, and review each `promoted → dropped` item.

### 3. Commit the result

## What it cannot check

- That each brief and report went to the right owner.
- That a synthesized title or description reads well — the run takes the H1 and
  the first sentence.
- That the result is committed.

## If you run it twice

A second run finds nothing in a retired folder, every owned file identical, the
config already patched and every template recorded, and changes no byte.

## Cross-Reference Updates

Every link to a moved document is respelled, in `docs/` and in tracked Markdown
outside it. Skills or scripts that name `docs/projects/` or another retired path
in code or prose are not links: `grep -rn "docs/projects/" .` finds them.
