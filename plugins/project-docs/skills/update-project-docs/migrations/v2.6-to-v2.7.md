# Migration: v2.6 → v2.7

## Summary

v2.7 puts a **checked metadata layer** on the documentation tree. Every document
gains an
[OKF 0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
frontmatter block, a lint reads that layer and gates commits and CI, and a new
`cycle` document type names the work currently in play.

**Nothing moves.** No file changes folder, no directory is renamed, no document
type is retired. This is additive: frontmatter on top of documents that already
exist, plus six new files and a `cycles/` directory.

This is what a migrated document's header looks like — the shape everything
below is working toward:

```yaml
---
type: lesson
title: Migration steps must be uniformly specific
description:
  In an agent-run guide, one underspecified step becomes the failure point.
tags: [migrations, agent-execution, documentation]
status: stable
generated: { by: unknown, at: 2026-03-03 }
---
```

**Why this changed:** the tree had grown a metadata layer by hand and nothing
checked any of it. Statuses were invented per-document because the vocabulary
had no word for the state (`Approved (in flight)` appeared in three separate
proposals in the scaffold repo), and a `**Status:**` line that nobody validates
drifts silently — of seventeen live proposals audited against the actual tree,
eleven claimed a state they were no longer in.

**Does this migration apply to you?** It applies if `docs/SCHEMA.md` does not
exist:

```bash
[ -f docs/SCHEMA.md ] && echo "already on v2.7 — skip this migration" || echo "run this migration"
```

Check that rather than the `docs_version` number. Version markers in **the
scaffold template** are bumped by release-please on every release, structural or
not, so `docs_version` in your project tells you which scaffold release you
copied from — not which structural migrations you have applied. The `vX-to-vY`
names in this skill's `## Available Migrations` table
([SKILL.md](../SKILL.md#available-migrations)) are labels in their own
structural sequence.

**Docs root.** Every path below is written as `docs/`. If your project already
has a `.project-docs.json` with a different `docsRoot`, substitute it throughout
— including in the applicability test above and the whole Verification section.
The migration script reads `docsRoot` itself and prints which root it is using;
the commands in this guide do not.

## What's New

| Path                 | What it is                                                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `docs/SCHEMA.md`     | The contract. Which fields every document carries, the two lint tiers, the lifecycle vocabularies.                                                     |
| `docs/index.md`      | The catalog. One line per library page; the reachability root the lint checks against.                                                                 |
| `docs/lint.ts`       | The entry point. `bun docs/lint.ts`, plus `--json` and `--report`.                                                                                     |
| `scripts/docs-lint/` | The portable core: `index.ts`, `config.ts`, `unlinted-links.ts`.                                                                                       |
| `docs/cycles/`       | The new document type — `README.md` and `TEMPLATE.md`.                                                                                                 |
| `.project-docs.json` | Root config: `docsRoot`, and `lint` with `adopting`, `exclude`, `durable`, `workbench`, `skip`. Written by the migration script in step 8, not copied. |

Every template under `docs/` also gains a frontmatter block, and the bold
`**Status:** / **Created:** / **Author:**` lines come out of them.

**Two fields where there was one.** `status` is OKF's own field and takes only
`draft | stable | deprecated` — whether the document can be trusted. `lifecycle`
is ours and says where the work has got to, with a vocabulary per type. The old
bold `**Status:**` line was carrying both questions in one value, which is why
it kept growing hyphenated states.

**Two lint tiers, keyed to the folder.** The **library** — `architecture/`,
`specifications/`, `interaction-design/`, `playbooks/`, `lessons-learned/`,
`memories/`, plus the root pages — is checked for catalog reachability and
`related:` edges as well as frontmatter. The **workbench** —
`backlog/ briefs/ investigations/ projects/ reports/ fragments/ cycles/` — is
checked for presence, vocabulary and links only. Workbench documents close and
nobody returns to them; making them carry graph obligations would be paperwork.

Two names for the library, unavoidably: prose calls it the library, and the
config key is `lint.durable`, because it is a list of folder names and the root
pages aren't folders. They are the same tier.

`related:` is an optional list of `type/slug` edges between library pages;
`docs/SCHEMA.md` defines it, and nothing in this migration writes one.

## What Moved

Nothing.

## What's Removed

The bold metadata lines at the top of **documents** — `**Status:**`,
`**Created:**`, `**Date:**`, `**Added:**`, `**Last Updated:**`,
`**Last Reviewed:**`, `**Author:**`, `**Investigator:**`, `**Tags:**` — are
removed by the migration script in step 8.

**Three of those are deleted, not migrated.** `**Author:**`, `**Investigator:**`
and `**Last Reviewed:**` have no frontmatter field to land in: `generated.by`
records the actor that produced the content, which is not the same claim. If
those lines matter to you, grep for them and save them before step 8:

```bash
grep -rn '^\*\*\(Author\|Investigator\|Last Reviewed\):' docs/ > /tmp/pre-migration-authors.txt
```

**Templates are replaced, not rewritten.** The script skips any file whose name
contains `template` and anything under a `TEMPLATES/` directory — it will not
touch them. Templates lose their bold lines because step 5 copies fresh ones
from the scaffold. Any template step 5's list doesn't cover keeps its bold lines
and needs a manual pass.

## Step-by-Step Migration

### [Agent] 1. Commit or stash your work first

The script in step 8 rewrites every document under your docs root in one pass.
It refuses to run against a dirty docs tree for that reason — a hundred-file
diff is only reviewable on its own.

```bash
git status --short -- docs/
```

Anything listed: commit it or stash it before continuing.

### [Agent] 2. Install Bun and cookiecutter

The lint and the migration script are Bun TypeScript. Bun is a single binary and
does not replace your package manager. Cookiecutter generates the scaffold in
step 3.

```bash
command -v bun || curl -fsSL https://bun.sh/install | bash
command -v cookiecutter || pipx install cookiecutter
bun --version && cookiecutter --version
```

### [Agent] 3. Generate the v2.7 scaffold locally

Two flags matter here. `--no-input` is required: without it cookiecutter prompts
interactively and hangs when there is no terminal. And
`install_target="New project folder"` is required **because `--no-input` picks
the first choice**, which is the current-directory install — that branch moves
the payload's `docs/` up into `.scaffold-tmp` and deletes the rest, leaving you
without the reference copy this migration reads from.

```bash
rm -rf .scaffold-tmp
cookiecutter gh:ichabodcole/project-docs-scaffold-template --no-input \
  -o .scaffold-tmp install_target="New project folder"
SCAFFOLD=$(ls -d .scaffold-tmp/*/ | head -1)
echo "scaffold at: $SCAFFOLD"
```

`$SCAFFOLD` is the generated **project root**, not its `docs/` — this migration
copies files from outside `docs/` as well. Verify:

```bash
ls "$SCAFFOLD/docs/SCHEMA.md" "$SCAFFOLD/scripts/docs-lint/index.ts"
```

### [Agent] 4. Copy the layer in

```bash
cp "$SCAFFOLD/docs/SCHEMA.md" docs/SCHEMA.md
cp "$SCAFFOLD/docs/index.md" docs/index.md
cp "$SCAFFOLD/docs/lint.ts" docs/lint.ts

mkdir -p scripts/docs-lint
cp "$SCAFFOLD/scripts/docs-lint/index.ts" scripts/docs-lint/index.ts
cp "$SCAFFOLD/scripts/docs-lint/config.ts" scripts/docs-lint/config.ts
cp "$SCAFFOLD/scripts/docs-lint/unlinted-links.ts" scripts/docs-lint/unlinted-links.ts

mkdir -p docs/cycles
cp "$SCAFFOLD/docs/cycles/README.md" docs/cycles/README.md
cp "$SCAFFOLD/docs/cycles/TEMPLATE.md" docs/cycles/TEMPLATE.md
```

**These are overwrites, not merges.** All eight files are new in v2.7, so there
is nothing of yours to preserve — unless you already have a `docs/index.md`, in
which case rename it first and fold its content back in at step 10.

Verify:

```bash
ls docs/SCHEMA.md docs/index.md docs/lint.ts docs/cycles/ scripts/docs-lint/
```

### [Agent] 5. Copy the templates

Every template gains a frontmatter block. Copy only the ones your project has —
`[ -f ... ] &&` skips the rest:

```bash
for t in \
  architecture/TEMPLATE.md \
  backlog/TEMPLATE.md \
  briefs/TEMPLATES/BRIEF.template.md \
  fragments/TEMPLATE.md \
  interaction-design/TEMPLATE.md \
  investigations/YYYY-MM-DD-TEMPLATE-investigation.md \
  lessons-learned/TEMPLATE.md \
  memories/TEMPLATE.md \
  playbooks/TEMPLATE.md \
  reports/YYYY-MM-DD-TEMPLATE-report.md \
  specifications/TEMPLATE-domain.md \
  specifications/TEMPLATE-overview.md \
  projects/TEMPLATES/DESIGN-RESOLUTION.template.md \
  projects/TEMPLATES/HANDOFF.template.md \
  projects/TEMPLATES/PLAN.template.md \
  projects/TEMPLATES/PROPOSAL.template.md \
  projects/TEMPLATES/TEST-PLAN.template.md \
  projects/TEMPLATES/YYYY-MM-DD-SESSION.template.md \
; do
  [ -f "docs/$t" ] && cp "$SCAFFOLD/docs/$t" "docs/$t" && echo "copied $t"
done
```

**Overwrite, unless you customized a template.** If you did, diff it first
(`diff "docs/$t" "$SCAFFOLD/docs/$t"`) and merge by hand: take the new
frontmatter block and the removal of the bold metadata lines, keep your body.

Verify that no template your project has kept a bold status line — the script in
step 8 will not remove them:

```bash
grep -rln '^\*\*Status:' docs/ | grep -i 'template'
```

Expect no output. Anything listed is a template step 5 didn't cover; strip its
bold lines and add a frontmatter block by hand, copying the shape from a
neighbour.

### [Agent] 6. Commit what you have copied

**Do not skip this.** Steps 4 and 5 wrote into `docs/`, and the script in step 8
refuses to run against a dirty docs tree — its whole purpose is to leave a
reviewable diff of its own. Committing here is also what makes step 8's diff
readable.

```bash
git add docs/ scripts/docs-lint/
git commit -m "docs: install the v2.7 frontmatter layer (files only)"
git status --short -- docs/    # expect no output
```

If you have a reason not to commit — a review workflow that wants one commit —
pass `--force` to the script in step 8 instead. It writes anyway, and the diff
you review will contain both the copies and the rewrites.

### [Agent] 7. Add the scripts to `package.json`

Add these five. **Merge, do not replace** — `test` and `check` are the two most
likely to already exist, and if yours does, append to it rather than overwriting
it (`"check": "<your existing check> && npm run docs:lint"`).

```json
{
  "scripts": {
    "docs:lint": "bun docs/lint.ts",
    "docs:graph": "bun docs/lint.ts --json",
    "docs:report": "bun docs/lint.ts --report",
    "test": "bun test",
    "check": "npm run format:check && npm run docs:lint && npm run test"
  }
}
```

`check` as written assumes a `format:check` script (Prettier). If your project
has no formatter, drop that clause. If your project has no `package.json` at
all, skip this step entirely and invoke `bun docs/lint.ts` directly everywhere
below.

Verify:

```bash
npm run docs:lint --silent >/dev/null 2>&1; echo "docs:lint wired: $?"
```

### [Agent] 8. Run the migration script

```bash
SKILL_DIR=$(dirname "$(dirname "$(realpath "$0" 2>/dev/null || echo .)")")
# Or set it directly to wherever this skill lives, e.g.:
# SKILL_DIR="$HOME/.claude/plugins/.../project-docs/skills/update-project-docs"

# Preview what will change (safe, writes nothing, ignores the dirty-tree guard)
bun "${SKILL_DIR}/migrations/scripts/migrate-v2.6-to-v2.7.ts" --dry-run

# Apply
bun "${SKILL_DIR}/migrations/scripts/migrate-v2.6-to-v2.7.ts"
```

The script derives what each file already knows: `type` from where it sits,
`title` from its H1, `lifecycle` from the bold `**Status:**` line it is about to
lose, `tags` from a bold tags line, and `generated.at` from a bold date line,
else a `YYYY-MM-DD-` filename prefix, else the file's first commit. It skips any
file that already has frontmatter, so it is safe to re-run.

**Three things it writes without being able to check them.** All three are step
9's job:

- **`status: stable`, on every document, unconditionally.** There is no signal
  in a v2.6 document that distinguishes a draft from a finished page, so the
  script writes the value that is true of most of them. A genuinely unreviewed
  page should be `draft`, and nothing will tell you which those are.
- **`lifecycle` falls back to the type's opening value** when there is no bold
  status line, or when the line is still the template's unfilled pick-list
  (`Draft | Active | Completed`). So a shipped proposal with no status line
  comes out as `draft`. This is not reported — it looks identical to a derived
  value.
- **It never writes `description`.** That is one sentence a person has to mean,
  and a generated paraphrase of the first paragraph would be worse than the
  blank — you would never be able to tell which ones had been thought about.

Two things it **does** report and leave for you:

- **Unmapped statuses** — a bold `**Status:**` value with no equivalent in the
  new vocabulary. The field is left blank; you decide.
- **Undated documents** — no date line, no dated filename and no first commit,
  set to `1970-01-01`.

**`.project-docs.json`:** the script creates it, with `lint.adopting: true` and
`version` copied from your `docs/README.md` marker. **If your project already
has one, the script leaves it alone** — in that case add the `lint` block by
hand, copying the shape from `$SCAFFOLD/.project-docs.json`.

Then run your formatter, since the script writes YAML without reflowing it:

```bash
npx prettier --write "docs/**/*.md"    # skip if the project has no Prettier
```

### [Agent] 9. Work the report

```bash
bun docs/lint.ts --report
```

This lists every document still missing a field, worst first, and **always exits
0** — it is a worklist, not a gate, so read its output rather than its exit
code. Mostly it will be `description`. Write them; one sentence each, saying
what the document is for, not what it is called.

While you are in each file, audit the two fields the script had to guess:

- **`lifecycle`** — check it against reality rather than against what the old
  bold line claimed. This is the part of the migration that finds things: a
  proposal marked `approved` whose feature shipped a year ago is `implemented`,
  and the difference is the whole reason the field exists.
- **`status`** — everything came out `stable`. Anything you would not want a
  reader to rely on is `draft`; anything kept only for its links and history is
  `deprecated`.

Do this before step 10. The catalog copies each page's `description`, so there
has to be one first.

### [Agent] 10. Fill the catalog

`docs/index.md` arrives from the scaffold with `_No pages yet._` under each
heading, one heading per library folder. Every **library** page needs a line;
workbench documents are deliberately not catalogued. The lint names the missing
ones:

```bash
bun docs/lint.ts 2>&1 | grep ORPHAN
```

Each line looks like:

```
ORPHAN         playbooks/writing-migrations.md  (unreachable from index.md — add its catalog line)
```

The path's first segment is the heading it goes under. Add a line there:

```markdown
- [Page title](./playbooks/writing-migrations.md) — the page's own
  `description`, copied verbatim.
```

**The hook after the dash must equal that page's `description` exactly.** The
lint compares the two and reports `STALE HOOK` on drift; that is what stops the
catalog from becoming a second, staler set of summaries. Re-run the grep until
it is empty.

### [Agent] 11. Open a cycle

The `cycle` type names what is in play right now. Create one from the template
you copied in step 4 — it documents every field, including the `scope:` list:

```bash
cp docs/cycles/TEMPLATE.md "docs/cycles/$(date +%Y-%m)-<slug>.md"
```

Replace `<slug>` with two or three kebab-case words naming the work. Then open
the file and fill it as its own comments direct: `lifecycle: active`, and
`scope:` as a YAML list of `project/<folder-name>` and
`backlog/<item-filename-without-.md>` entries for the work currently underway.
**At most one cycle may be `active`**; the lint enforces it.

Verify:

```bash
bun docs/lint.ts && echo "cycle accepted"
```

This step is optional in the sense that the lint passes with an empty
`docs/cycles/`. Skipping it leaves you with the type installed and nothing using
it, which is a fine place to stop if no work is in play today.

### [Agent] 12. Turn the gate on

When `bun docs/lint.ts --report` comes back with nothing listed, set
`lint.adopting` to `false`. **Edit that one key in place** — do not replace the
file, which would drop `docsRoot`, `durable`, `workbench` and `skip`:

```bash
# find:    "adopting": true
# replace: "adopting": false
grep -n '"adopting"' .project-docs.json
```

While `adopting` is `true` the lint reports problems and exits 0, saying so on
every run. That exists so a project can adopt the layer over several commits
without a red gate the whole time. Leaving it `true` permanently means the gate
never gates.

Then wire it in. Pre-commit, if the project uses husky:

```bash
echo 'npm run check' > .husky/pre-commit
chmod +x .husky/pre-commit
```

And CI — add a job to your workflow, or create
`.github/workflows/docs-check.yml`:

```yaml
name: Docs check
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: npm ci
      - run: npm run check
```

### [Agent] 13. Update the version markers and clean up

Both markers carry the same value: the scaffold release you migrated from, which
is the `docs_version` in the scaffold's own `docs/README.md`.

```bash
VERSION=$(grep -m1 docs_version "$SCAFFOLD/docs/README.md" | sed 's/.*"\(.*\)".*/\1/')
echo "migrating to $VERSION"

# docs/README.md frontmatter
sed -i.bak -E "s/^docs_version: \".*\"/docs_version: \"$VERSION\"/" docs/README.md && rm docs/README.md.bak

# .project-docs.json — the script wrote your OLD version here, so the two never
# disagreed mid-migration. This moves both forward together.
sed -i.bak -E "s/(\"version\": )\"[^\"]*\"/\1\"$VERSION\"/" .project-docs.json && rm .project-docs.json.bak
```

Confirm they agree, then remove the scaffold:

```bash
grep docs_version docs/README.md
grep '"version"' .project-docs.json
rm -rf .scaffold-tmp
```

## Cross-Reference Updates

**No path changes in this migration**, so no link needs rewriting for structural
reasons.

One class of link does get **found** by the new lint rather than changed by it:
inbound references to projects that were archived after the referring document
was written. The scaffold repo's own first run turned up 31 broken links, 12 of
them exactly that.

```bash
bun docs/lint.ts 2>&1 | grep 'MISSING FILE'
```

The rewrite inserts `_archive/` immediately before the project name, at whatever
depth the link was written:

| Broken                    | Fixed                              |
| ------------------------- | ---------------------------------- |
| `../projects/foo/plan.md` | `../projects/_archive/foo/plan.md` |
| `../foo/proposal.md`      | `../_archive/foo/proposal.md`      |
| `./foo/`                  | `./_archive/foo/`                  |

**One exception:** a `../<name>/` link from a document that is itself already
under `_archive/` fixes itself when the target moves. Leave those alone;
rewriting produces `_archive/_archive/<name>/`.

## Verification

```bash
# The layer is installed
ls docs/SCHEMA.md docs/index.md docs/lint.ts .project-docs.json
ls scripts/docs-lint/index.ts scripts/docs-lint/config.ts scripts/docs-lint/unlinted-links.ts
ls docs/cycles/README.md docs/cycles/TEMPLATE.md

# The scripts are wired
grep -q '"docs:lint"' package.json && echo "scripts present"

# Every document has frontmatter, and the gate is green
bun docs/lint.ts && echo "PASS"

# The worklist is empty — expect no lines naming a file
bun docs/lint.ts --report

# No template kept a bold status line (matches TEMPLATE anywhere in the name)
grep -rln '^\*\*Status:' docs/ | grep -i 'template' && echo "FAIL" || echo "templates clean"

# The gate actually gates
grep '"adopting"' .project-docs.json      # expect: false

# The two version markers agree
grep docs_version docs/README.md
grep '"version"' .project-docs.json

# The graph emits
bun docs/lint.ts --json | head -20

# Scaffold cleanup
[ ! -d .scaffold-tmp ] && echo "cleaned"
```
