# Migration: v2.6 → v2.7

## Summary

v2.7 puts a **checked metadata layer** on the documentation tree. Every document
gains an
[OKF 0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
frontmatter block, a lint reads that layer and — once you turn it on — gates
commits and CI, and a new `cycle` document type names the work currently in
play.

**Nothing moves.** No file changes folder, no directory is renamed, no document
type is retired. This is additive: frontmatter on top of documents that already
exist, plus the tooling, the contract, the catalog and a `cycles/` directory.

This is what a migrated document's header looks like — the shape the script
writes, minus the one line it leaves to you:

```yaml
---
type: lesson
title: Migration steps must be uniformly specific
description:
  In an agent-run guide, one underspecified step becomes the failure point.
tags: [migrations, agent-execution, documentation]
status: stable
generated: { by: unknown, at: 2026-03-03 }
---
```

**Why this changed:** the tree had grown a metadata layer by hand and nothing
checked any of it. A `**Status:**` line nobody validates drifts silently, and
the vocabulary grew hyphenated states to cover what it had no word for.

**Does this migration apply to you?** It applies while either half of the layer
is missing — the contract or the tooling that reads it:

```bash
{ [ ! -f docs/SCHEMA.md ] || [ ! -f scripts/pdocs/cli.ts ]; } || { echo "docs/SCHEMA.md and scripts/pdocs/cli.ts are both here — the layer is in; this migration does not apply"; exit 1; }
```

Check that rather than the `docs_version` number. Version markers in **the
scaffold template** are bumped by release-please on every release, structural or
not, so `docs_version` in your project tells you which scaffold release you
copied from — not which structural migrations you have applied. The `vX-to-vY`
names in this skill's `## Available Migrations` table
([SKILL.md](../SKILL.md#available-migrations)) are labels in their own
structural sequence.

**Both halves, because a tree can have one without the other.** `docs/` copied
from a generated project without `scripts/` — the partial adoption
`update-project-docs` § Step 7 describes — has the contract and nothing that
checks it. The test above is true on it, and the script does not refuse it
either: each phase tests its own precondition, so on such a tree the layer is
installed and the phases that find their work already done say so and continue.

**Where it hands off.** This script ends with the layer installed and the gate
off. `update-project-docs` § Step 4 runs migrations in sequence, and the next
one is [v2.8-to-v2.9](./v2.8-to-v2.9.md), whose precondition
`[ ! -f docs/.pdocs-seed.json ]` is true on the tree this script leaves. It can
run before the backfill — its verify phase requires `pdocs check` to exit 0,
which it does while `lint.adopting` is `true`.

**Docs root.** Every path below is written as `docs/`. The script reads
`docsRoot` from `.project-docs.json` when your project already has one and
prints which root it is using; otherwise it is `docs/`, and the config it writes
says so.

**This migration installs today's tooling, not a v2.7 snapshot.** The scaffold
phase generates from the **live** template, so what arrives is the current
`pdocs` CLI under `scripts/pdocs/` and the current `docs/SCHEMA.md`.

**What changes in your tree:** `scripts/pdocs/` is installed, `docs/SCHEMA.md`
is installed, `docs/index.md` is installed if you have none, `docs/cycles/` is
created with its README, every template the scaffold ships is installed or
replaced, every document under `docs/` gains a frontmatter block and loses its
bold metadata lines, `.project-docs.json` is created with `lint.adopting: true`,
and both version markers are set. No document body is changed beyond the bold
lines the block replaces, and no `description` is written anywhere.

## This migration is a script

One command does the whole migration. Every phase verifies itself, and any
failure stops the run with a non-zero exit and a named reason — including
failures the script did not anticipate. Every stop also says whether the tree
was written to: `Nothing was written.` or
`The tree may be partly migrated. Re-running is safe`.

**Why, in two sentences you can check yourself.** The guide this replaces set
`SCAFFOLD=$(ls -d .scaffold-tmp/*/ | head -1)` in one shell block and read it in
three others, and an agent runs each block in a **different process** — so by
the copy step the value was empty and `cp "$SCAFFOLD/docs/SCHEMA.md"` copied
from `/docs/SCHEMA.md` at exit 0. Its checks were `&& echo ok || echo STOP`,
which exits 0 either way; one process and real exit codes make both impossible
rather than discouraged.

**Where it stops.** Tooling installed, codemod run, `pdocs report` printed, exit
0, and the **gate off** — `lint.adopting: true`. The lint requires `description`
on every document and the codemod deliberately does not write one, so a fresh
migration cannot pass the gate. The backfill, the catalog and turning the gate
on are [steps you take after the script](#after-the-script), not phases in it.

## What's New

| Path                       | What it is                                                                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docs/SCHEMA.md`           | The contract. Which fields every document carries, the two lint tiers, the lifecycle vocabularies, and who owns which file.                          |
| `docs/index.md`            | The catalog. One line per library page; the reachability root the lint checks against. Installed as a skeleton if you have none; yours from then on. |
| `scripts/pdocs/`           | The `pdocs` CLI — the entry point. `bun scripts/pdocs/cli.ts check`, plus `report`, `graph`, `find`, `backlinks`, `orphans` and `new`.               |
| `scripts/pdocs/docs-lint/` | The portable core, inside `pdocs/` so your `scripts/` gains one directory, not two.                                                                  |
| `docs/cycles/`             | The new document type — `README.md` and `TEMPLATE.md`.                                                                                               |
| `.project-docs.json`       | Root config: `docsRoot`, `version`, and `lint` with `adopting`, `exclude`, `durable`, `workbench`, `skip`. Written by the script, not copied.        |

Every template under `docs/` also gains a frontmatter block, and the bold
`**Status:** / **Created:** / **Author:**` lines come out of them.

**Two fields where there was one.** `status` is OKF's own field and takes only
`draft | stable | deprecated` — whether the document can be trusted. `lifecycle`
is ours and says where the work has got to, with a vocabulary per type. The old
bold `**Status:**` line was carrying both questions in one value, which is why
it kept growing hyphenated states.

**Two lint tiers, keyed to the folder.** The **library** — `architecture/`,
`specifications/`, `interaction-design/`, `playbooks/`, `lessons-learned/`,
`memories/`, plus the root pages — is checked for catalog reachability and
`related:` edges as well as frontmatter. The **workbench** —
`backlog/ briefs/ investigations/ projects/ reports/ fragments/ cycles/` — is
checked for presence, vocabulary and links only. The config key for the library
is `lint.durable`; they are the same tier. **A folder in neither list is read as
library**, with every page in it of unknown type — which is why the script's
first phase stops on one rather than letting you find out from the gate.

## What Moved

Nothing.

## What's Removed

The bold metadata lines at the top of **documents** — `**Status:**`,
`**Created:**`, `**Date:**`, `**Added:**`, `**Last Updated:**`,
`**Last Reviewed:**`, `**Author:**`, `**Investigator:**`, `**Tags:**` — are
removed by the frontmatter phase, which consumes what it can into the block.

**Three of those are deleted, not migrated.** `**Author:**`, `**Investigator:**`
and `**Last Reviewed:**` have no frontmatter field to land in: `generated.by`
records the actor that produced the content, which is not the same claim. If
those lines matter to you, save them **before** running the script:

```bash
grep -rn '^\*\*\(Author\|Investigator\|Last Reviewed\):' docs/ > /tmp/pre-migration-authors.txt
```

**Templates are replaced, not rewritten.** The frontmatter phase skips any file
whose name contains `template` and anything under a `TEMPLATES/` directory; the
templates phase replaces a v2.6 template — one with no frontmatter block — from
the scaffold instead. A template you had already given a frontmatter block is
kept and named; see [What it does not do](#what-it-does-not-do).

## Run it

```bash
cd <your project root>              # the directory holding docs/
SKILL_DIR=<the update-project-docs skill directory>
bun "$SKILL_DIR/migrations/scripts/migrate-v2.6-to-v2.7.ts" --dry-run
```

Set `SKILL_DIR` in the **same** block you use it in, or paste the literal path —
a shell variable does not survive into a separate command. An agent that loaded
`update-project-docs` has the directory as its "Base directory for this skill";
otherwise it is two levels above this file. `bun` must be on PATH: the script
runs under it, and so does the gate it installs.

The dry run generates the scaffold, changes nothing in your project, and prints
what each phase would do. A run without `--scaffold-dir` lets cookiecutter write
outside `--root`: its clone cache in `~/.cookiecutters/` and a replay file in
`~/.cookiecutter_replay/`, as the v2.9 script's does. **Three things to read in
it:**

- **The preflight's tier report.** On a real tree the expected first outcome is
  a stop naming a folder under `docs/` that holds markdown and is in no lint
  tier — `runbooks/`, `decisions/`, whatever your project grew. Declare it or
  skip it in `.project-docs.json` (the message prints the exact lines to paste,
  and the script fills in whatever else the file needs), then re-run. The stop
  is deliberate: the alternative is that folder silently getting the strictest
  checks. A folder holding no markdown the lint would read — an empty
  placeholder, an `.obsidian/` of JSON, one whose files all match a
  `lint.exclude` glob — is reported with a `·` and left alone.
- **The template list.** Each one is `install`, `replace`, `already in place` or
  `kept`; on a v2.6 tree every existing template is `replace`, because a v2.6
  template has no frontmatter block.
- **The frontmatter list.** One line per document that gains a block, with the
  `type` and `lifecycle` derived for it. A `lifecycle` you disagree with is
  cheaper to fix now than after the block is written.

Then:

```bash
bun "$SKILL_DIR/migrations/scripts/migrate-v2.6-to-v2.7.ts"
```

Commit the result **on its own**, before the backfill. The diff is then
reviewable as "the tooling arrived" separately from "the descriptions were
written".

### Options

| Flag                 | When you need it                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `--root <path>`      | The project to migrate. Defaults to the current directory.                                                                              |
| `--dry-run`          | Report every phase's plan; change nothing in the project. The scaffold is still generated, and removed.                                 |
| `--scaffold-dir <p>` | Use a scaffold you already generated instead of fetching one. Skips the network and the `cookiecutter` check. `--scaffold` is an alias. |

Exit codes: `0` success · `1` the migration could not complete · `2` bad
invocation.

## What it does, phase by phase

1. **Preflight** — confirms this is a project-docs tree (`docs/README.md` exists
   and carries a `docs_version` line — a v2.6 tree has no `.project-docs.json`
   yet, so that is the test), resolves `docsRoot`, requires `bun` on PATH and
   `cookiecutter` (unless `--scaffold-dir`), reports a dirty git tree, and
   **stops on any folder under `docs/` that holds markdown the lint would read
   and is in no lint tier and not in `lint.skip`**, naming each one and printing
   the config lines that declare or skip it; a folder holding none is reported
   and left alone. The dirty tree is reported, not enforced. Two more stops
   here, before anything is written: a tree with no `docs_version` is pre-2.0
   (`v1-to-v2` comes first), and a `.project-docs.json` with
   `lint.adopting: false` is a tree that has finished adopting — refreshing its
   layer is `v2.8-to-v2.9`'s job, not this script's.
2. **Scaffold** — generates the current template into a private temp directory,
   never into your project, and verifies the result has `docs/SCHEMA.md` and
   `scripts/pdocs/`. A dry run generates it too. The scaffold's `docs_version`
   is the release both markers end at; a scaffold whose `docs/README.md` has no
   parsable `docs_version` stops the run. The temp directory is removed however
   the run ends.
3. **Install the layer** — `scripts/pdocs/` (**owned**: replaced; the copy
   merges, so a file a later release removed would survive), `docs/SCHEMA.md`
   (**owned**: replaced, and must carry the "Who owns which file" section — an
   older scaffold stops the run), `docs/index.md` (**theirs**: installed only if
   absent, never overwritten), and any category folder the scaffold has that you
   do not, created with its README. A folder it would create that is in no tier
   of your `.project-docs.json` stops the run first, before anything is written,
   with the same paste lines as the preflight. Each item reports installed,
   replaced, already identical, or left alone.
4. **Install the templates** — every file the scaffold ships whose name contains
   `TEMPLATE` and ends `.md`, or ends `.template.md` (**seeded**). A missing one
   is **installed**. A template with no frontmatter block is a v2.6 one and is
   **replaced**, because it fails the lint as it is. A template that already
   carries a block — your edit — is **kept** and named, whether or not
   `docs/.pdocs-seed.json` exists yet. A scaffold template without a frontmatter
   block stops the run.
5. **Frontmatter on every document** — the codemod. Derives `type` from where
   the file sits, `title` from its H1, `lifecycle` from the bold `**Status:**`
   line it removes, `tags` from a bold tags line, and `generated.at` from a bold
   date line, else a `YYYY-MM-DD-` filename prefix, else the file's first
   commit. Skips any file that already opens with `---`, every README, template
   and contract page, and everything under `_archive/` or a `lint.exclude` glob.
   Reports each file it marks, then the statuses it could not map (left blank)
   and the documents it could not date (`1970-01-01`). Never stops.
6. **`.project-docs.json`** — created with `lint.adopting: true`, the tier
   arrays, and `version` **carried forward** from `docs/README.md`, never
   invented, so the two markers never disagree mid-run. If the file already
   exists it is parsed, only the keys it lacks are added, and it is
   re-serialised; every key you wrote stays as it was.
7. **The worklist** — runs `bun scripts/pdocs/cli.ts report --format text` from
   your project and prints it. This is what [the backfill](#1-the-backfill)
   works from. A CLI that cannot read the tree stops the run.
8. **Version markers** — sets `docs_version` in `docs/README.md` and `version`
   in `.project-docs.json` to the scaffold's release, reporting each separately.
   The JSON is parsed and re-serialised rather than pattern-substituted, so only
   the top-level key can move.
9. **Cleanup** — removes the generated scaffold. A supplied `--scaffold-dir` is
   left in place.

**Then the script checks its own work.** Before exiting 0 it re-reads the tree
and confirms what the phase ordering guarantees: `.project-docs.json` exists
with `lint.adopting: true` and the scaffold's version; no folder the lint reads
is left undeclared by that config; every template the scaffold ships is in place
with a frontmatter block; the codemod has nothing left to do; the worklist it
printed still matches the tree; the README marker moved with the config's;
`pdocs check` exits 0 on the result; and the generated scaffold is gone. Any
line that does not hold fails the run and names the phase responsible, so the
ordering is enforced rather than merely intended.

## After the script

Four things the script leaves to you, in this order. The first three are what
the gate needs; the fourth is a choice.

### 1. The backfill

```bash
bun scripts/pdocs/cli.ts report --format text
```

The worklist the script printed, re-runnable. It lists every document still
missing a field, worst first, and **always exits 0** — read its output, not its
exit code. Mostly it will be `description`: one sentence per document, saying
what the document is for, not what it is called. It has to be true, which is why
no script writes it.

While you are in each file, audit the two fields the codemod had to guess:

- **`lifecycle`** — check it against reality rather than against what the old
  bold line claimed. This is the part of the migration that finds things: a
  proposal marked `approved` whose feature shipped a year ago is `implemented`,
  and the difference is the whole reason the field exists.
- **`status`** — everything came out `stable`. Anything you would not want a
  reader to rely on is `draft`; anything kept only for its links and history is
  `deprecated`.

The precedent is the scaffold repository's own backfill — commit `ada5b7e`, "the
backfill, and what checking 137 documents turned up" — for both the effort and
what it turns up.

### 2. Fill the catalog

`docs/index.md` arrived with `_No pages yet._` under each heading, one heading
per library folder. Every **library** page needs a line; workbench documents are
deliberately not catalogued. `pdocs orphans` names the missing ones:

```bash
bun scripts/pdocs/cli.ts orphans --format text
```

Each orphan is one indented, repo-relative path. The segment after your docs
root is the heading it goes under. Add a line there:

```markdown
- [Page title](./playbooks/writing-migrations.md) — the page's own
  `description`, copied verbatim.
```

**The hook after the dash must equal that page's `description` exactly.** The
lint compares the two and reports `STALE HOOK` on drift. That is why this step
comes **after** the backfill — a catalog written before the descriptions exist
is a catalog written twice — and **before** the gate: the graph tier checks
catalog reachability, so the gate cannot go on with orphans. Re-run `orphans`
until it says `none`; it always exits 0, so read its output, not its exit code.

### 3. Turn the gate on

Two things, not one. A flag flipped with nothing running the check is not a
gate.

**First,** when `bun scripts/pdocs/cli.ts report --format text` lists nothing
and `orphans` says `none`, set `lint.adopting` to `false`. **Edit that one key
in place** — do not replace the file, which would drop `docsRoot`, `durable`,
`workbench` and `skip`:

```bash
# find:    "adopting": true
# replace: "adopting": false
grep -n '"adopting"' .project-docs.json
```

While `adopting` is `true` the lint reports problems and exits 0, saying so on
every run. That exists so a project can adopt the layer over several commits
without a red gate the whole time. Leaving it `true` permanently means the gate
never gates.

**Second,** wire it in. Pre-commit, if the project uses husky — this adds the
line to the hook such a project already has, and creates the hook otherwise:

```bash
grep -qx 'npm run check' .husky/pre-commit 2>/dev/null || echo 'npm run check' >> .husky/pre-commit
chmod +x .husky/pre-commit
```

And CI — add a job to your workflow, or create
`.github/workflows/docs-check.yml`:

```yaml
name: Docs check
on: [push, pull_request]
jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: oven-sh/setup-bun@v2
      - run: npm ci
      - run: npm run check
```

Both assume a `check` script. The scaffold ships no `package.json`, so add it to
yours:

```json
{
  "scripts": {
    "check": "bun scripts/pdocs/cli.ts check --format text"
  }
}
```

`--format text` is pinned on purpose: `pdocs` renders text on a terminal and
JSON everywhere else, and CI has no TTY — without the flag the hook prints text
and the CI job prints JSON, from one command.

Commit this separately from the backfill.

### 4. Choose a first cycle — optional

The `cycle` type names what is in play right now. The lint passes with an empty
`docs/cycles/`, so this is a person's call, not a migration step. To open one:

```bash
cp docs/cycles/TEMPLATE.md "docs/cycles/$(date +%Y-%m)-<slug>.md"
```

Replace `<slug>` with two or three kebab-case words naming the work, then fill
the file as its own comments direct: `lifecycle: active`, and `scope:` as a YAML
list of `project/<folder-name>` and `backlog/<item-filename-without-.md>`
entries. **At most one cycle may be `active`**; the lint enforces it.

## What it cannot check

- **That the result is committed**, and committed alone. The script leaves the
  tree dirty on purpose; the commit is yours.
- **That any `description` is true.** It writes none; the backfill is a person
  meaning one sentence per document.
- **That `lifecycle` and `status` match reality.** It derived the first from a
  bold line that may itself have been stale, and wrote `stable` for the second
  everywhere.
- **That the catalog hooks say what the pages say.** The lint catches drift once
  the gate is on; it cannot catch a hook that matches a description that is
  wrong.
- **That the gate is wired**, not merely enabled — `lint.adopting: false` with
  nothing running `pdocs check` is a flag, not a gate.
- **That the cycle you open is the right one**, or that opening none is.

## What it does not do

It writes no `docs/.pdocs-seed.json`, so it negotiates nothing. The seeded
mechanism — a template updated only while you have not edited it — starts when
`v2.8-to-v2.9` records the templates and `scripts/pdocs/seed.ts` has a record to
compare against. What this script can do is what `docs/SCHEMA.md` § "Who owns
which file" says of a first migration: adopt your tree as it stands. A template
with no frontmatter block is a v2.6 one and is replaced; a template that already
carries a block is someone's edit and is kept, named in the output, manifest or
no manifest.

## If you run it twice

Re-running is safe. Every phase reports what it finds already done and
continues: `scripts/pdocs/ already installed and identical`,
`docs/SCHEMA.md already identical`, `docs/index.md is there — left alone`, every
template `already in place`, `nothing to mark`, `lint.adopting already true`,
both markers `already at`. The tree is byte-identical afterwards.

The same is true of a tree that arrived with part of the layer — `docs/` copied
from a generated project without `scripts/`. There the layer phase installs
`scripts/pdocs/`, the templates phase finds every template in place, and the
config phase creates the file the tree never had.

## Cross-Reference Updates

**No path changes in this migration**, so no link needs rewriting for structural
reasons.

One class of link does get **found** by the new lint rather than changed by it:
inbound references to projects that were archived after the referring document
was written.

```bash
bun scripts/pdocs/cli.ts check --format text 2>&1 | grep 'MISSING FILE'
```

The rewrite inserts `_archive/` immediately before the project name, at whatever
depth the link was written:

| Broken                    | Fixed                              |
| ------------------------- | ---------------------------------- |
| `../projects/foo/plan.md` | `../projects/_archive/foo/plan.md` |
| `../foo/proposal.md`      | `../_archive/foo/proposal.md`      |
| `./foo/`                  | `./_archive/foo/`                  |

**One exception:** a `../<name>/` link from a document that is itself already
under `_archive/` fixes itself when the target moves. Leave those alone;
rewriting produces `_archive/_archive/<name>/`.

## Verification

The script checks all of this itself and stops on any failure, so this is what
to look for in its output rather than commands to run.

- [ ] `✓ every folder under docs/ the lint reads is in a tier or skipped (…)` —
      on a real tree the first run usually stops here instead, naming a folder;
      that is the check working. A line above it reading
      `· docs/<folder>/ is in no tier, and holds no markdown the lint reads` is
      a report, not a problem
- [ ] `✓ generated at <path>` (or `✓ using <path>` with `--scaffold-dir`)
- [ ] `✓ scripts/pdocs/ installed (N file(s) written; …)`,
      `✓ docs/SCHEMA.md installed`, `✓ docs/index.md installed (…)`, and
      `✓ docs/cycles/ created, with its README.md`. On a re-run, or on a tree
      that already had part of the layer, the first two read
      `✓ … already identical to the scaffold's`, and the last two are `·` notes
      instead: `· docs/index.md is there — left alone, it is yours` and
      `· every category folder the scaffold ships is already here`
- [ ] `✓ N template(s): I installed, M replaced (…), K already in place, J kept`
      — `N` is the scaffold's count (19 today); on a v2.6 tree `M` is every
      template you had, and each kept one has a `· kept …` line above naming why
- [ ] `✓ N document(s) gained frontmatter; M skipped (…)` — with one `✓` line
      per document above it, each naming its `type`
- [ ] `✓ created — lint.adopting: true (…), version <yours> carried from docs/README.md`
- [ ] ``✓ `pdocs report --format text` — the backfill's worklist`` followed by
      the report: expect `description` to head it
- [ ] `✓ docs/README.md set to <release>` and
      `✓ .project-docs.json set to <release>`, the same release on both
- [ ] `✓ generated scaffold removed`
- [ ] `Migration complete. The gate is off (lint.adopting: true); …` and
      **exit 0.** The exit code is the check; the lines above tell you which
      phase produced it
- [ ] `git status` shows the migration's changes and nothing else, and they are
      committed before the backfill begins. **The script cannot check this.**
