# Migration: v2.8 → v2.9

## Summary

v2.9 changes who owns your templates. Until now every migration copied the
scaffold's templates over yours, so tailoring one meant losing the edit at the
next upgrade. From v2.9 the templates are **seeded**: the scaffold installs a
working default, `docs/.pdocs-seed.json` records what it installed, and a later
migration updates a template only while you have not touched it — reporting it,
rather than overwriting it, once you have.

It also opens the document-type vocabulary. A project can declare its own folder
(`docs/runbooks/` carrying `type: runbook`) in `.project-docs.json` and the lint
accepts it.

Nothing you have written changes. This migration adds a file, refreshes the CLI
and `docs/SCHEMA.md`, and leaves every template exactly as it is.

## What's New

- **`docs/.pdocs-seed.json`** — the seed manifest. Docs-root-relative path →
  sha256 of the bytes the scaffold installed.
- **`scripts/pdocs/seed.ts`** — reads it back and decides, per file: `update`,
  `install`, `keep-modified`, `keep-unknown`, `keep-deleted`.
- **`lint.types` in `.project-docs.json`** — declare your own folders and the
  `type` their pages carry.
- **`pdocs find --type` now refuses an unknown type**, naming the set it knows.
  It used to return `count: 0` at exit 0, which reads as "nothing matches".
- **A "Who owns which file" section in `docs/SCHEMA.md`** — three classes:
  owned, seeded, theirs.

## What Moved

Nothing.

## What's Removed

Nothing.

## Step-by-Step Migration

### [Agent] 1. Commit or stash your work first

```bash
git status --short
```

Expected: no output. If there is any, commit or stash before continuing — this
migration rewrites `docs/SCHEMA.md` and `scripts/pdocs/`, and a dirty tree makes
its changes indistinguishable from yours.

### [Agent] 2. Confirm Bun and cookiecutter are available

```bash
bun --version && cookiecutter --version
```

Expected: a version from each. Both are required; stop if either is missing.

### [Agent] 3. Generate the current scaffold locally

```bash
cookiecutter gh:ichabodcole/project-docs-scaffold-template --no-input \
  -o .scaffold-tmp install_target="New project folder"
SCAFFOLD=$(ls -d .scaffold-tmp/*/ | head -1)
echo "scaffold at: $SCAFFOLD"
```

Verify this is the **project root**, not its `docs/`:

```bash
[ -f "$SCAFFOLD/docs/SCHEMA.md" ] && [ -d "$SCAFFOLD/scripts/pdocs" ] \
  && echo "SCAFFOLD ok: $SCAFFOLD" || echo "STOP — wrong path"
```

`$SCAFFOLD` is lost if your shell restarts. Re-run the two lines above before
steps 4, 5 and 9, or paste the literal path. An empty `$SCAFFOLD` makes step 4
copy from `/scripts/pdocs/` **at exit 0**.

### [Agent] 4. Refresh the CLI

`scripts/pdocs/` is _owned_ — it is delivered, not handed over, and this
replaces it wholesale. `seed.ts` arrives with it.

```bash
cp -R "$SCAFFOLD/scripts/pdocs/." scripts/pdocs/
```

Verify:

```bash
[ -f scripts/pdocs/seed.ts ] && echo "seed.ts installed" || echo "STOP — missing"
```

### [Agent] 5. Refresh `docs/SCHEMA.md`

Also _owned_: the lint implements it, so your copy has to match.

```bash
cp "$SCAFFOLD/docs/SCHEMA.md" docs/SCHEMA.md
```

Verify both new sections arrived:

```bash
grep -c 'Who owns which file' docs/SCHEMA.md
grep -c 'Declaring your own folder' docs/SCHEMA.md
```

Expected: `1` from each.

### [Agent] 6. Adopt your templates

This is the step the migration exists for. It records the sha256 of the
templates **already in your project** — not the scaffold's copies — so whatever
you have becomes the baseline.

First set `SKILL_DIR` to the directory this guide is in. **An agent reading this
already has it** — it is the "Base directory for this skill" stated when
`update-project-docs` was loaded. Set it literally:

```bash
SKILL_DIR="<the update-project-docs skill directory>"
```

Confirm it before using it, because an empty `SKILL_DIR` makes the next command
look for `/migrations/...` and fail in a way that reads like a missing script:

```bash
[ -f "${SKILL_DIR}/migrations/scripts/migrate-v2.8-to-v2.9.ts" ] \
  && echo "SKILL_DIR ok" || echo "STOP — set SKILL_DIR to the skill directory"
```

Look before you write. `--dry-run` lists every template it would record and
changes nothing:

```bash
bun "${SKILL_DIR}/migrations/scripts/migrate-v2.8-to-v2.9.ts" --dry-run
```

Then run it:

```bash
bun "${SKILL_DIR}/migrations/scripts/migrate-v2.8-to-v2.9.ts"
```

Verify:

```bash
[ -f docs/.pdocs-seed.json ] && echo "manifest written" || echo "STOP"
grep -c '"files"' docs/.pdocs-seed.json
```

Expected: `manifest written`, then `1`.

**What this does not do.** It compares nothing and replaces nothing. On this run
nothing is known — your project has no record of what the scaffold once
installed — so every template is adopted as it stands. A template you edited
three versions ago is recorded as though it had shipped that way. That is the
honest answer, and it is why this is a one-time adoption rather than a
reconciliation. From the next migration on, the comparison runs.

### [Agent] 7. Run the formatter

```bash
npx prettier --write "docs/**/*.md"
```

Skip if your project does not use Prettier.

### [Agent] 8. Verify the tree against the CLI

```bash
bun scripts/pdocs/cli.ts check
```

Expected: `docs-lint: clean`, exit 0. Then confirm the new refusal works:

```bash
bun scripts/pdocs/cli.ts find --type nosuchtype; echo "exit: $?"
```

Expected: a rejection naming the types it knows, **exit 2** — not an empty
result at exit 0.

### [Agent] 9. Update the version markers and clean up

Both markers carry the scaffold release you migrated TO.

```bash
VERSION=$(grep -m1 docs_version "$SCAFFOLD/docs/README.md" | sed 's/.*"\(.*\)".*/\1/')
echo "migrating to $VERSION"

sed -i.bak -E "s/^docs_version: \".*\"/docs_version: \"$VERSION\"/" docs/README.md && rm docs/README.md.bak
sed -i.bak -E "s/(\"version\": )\"[^\"]*\"/\1\"$VERSION\"/" .project-docs.json && rm .project-docs.json.bak
```

Confirm they agree, then remove the scaffold:

```bash
grep docs_version docs/README.md
grep '"version"' .project-docs.json
rm -rf .scaffold-tmp
```

## Cross-Reference Updates

None. No path changed and no document type was added or removed.

## Optional: declare your own document type

Not part of the migration — do it whenever you want one. To add `docs/runbooks/`
carrying `type: runbook`:

```jsonc
// .project-docs.json
"lint": {
  "workbench": ["backlog", "briefs", "...", "runbooks"],
  "types": { "runbooks": "runbook" }
}
```

The tier follows from the array you list the folder in: `workbench` for the thin
checks, `durable` for the full graph tier including catalog reachability. A
declared type is lintable but not creatable — `pdocs new` ships no template for
it and says so. `docs/SCHEMA.md` has the detail.
